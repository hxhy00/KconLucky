## 1. 系统概述

这是 KCon 2026 大会现场使用的一套**签到 + 抽奖 + 兑奖**系统，同一台服务器上并行运行两套辅助系统：**赠票分发**系统与**会议官网 + MCP 后端**。

| 子系统 | 源码位置 | 负责什么 | 不负责什么 |
|---|---|---|---|
| **KconLucky**（主系统） | 本仓库根目录（`ruoyi/`、`ruoyi-ui/`、`checkin-h5/`、`screen/`） | 现场签到、抽奖大屏、奖品与权益发放、兑奖核销、参会人名单与数据看板 | 会前赠票资格审批 |
| **赠票系统**（gift-system） | `gift-system/` | 会前「渠道 → 推荐人 → 赠票接收人」三级分发与审批、注册码邮件下发 | 现场签到（已禁用） |
| **官网 + MCP 后端**（详见 §11） | 服务器 `/opt/kcon2026/`（仓库内无副本） | 会议信息展示、议题投稿、反馈收集、AI 客户端接入（MCP） | 签到、抽奖、赠票 |

主系统与赠票系统**数据不互通**：赠票系统导出 CSV，由运营在主办方系统「名单导入」以追加模式人工导入，单向、手动触发。

三个子系统的源码各自独立、技术栈完全不同（Java + Docker Compose / 纯 Python 标准库 / Flask + MCP），详见 §12 的源码索引。

现场流程：

1. 参会者在手机 H5 上输入手机号或手机尾号，查询到本人后点击确认，完成签到；
2. 签到成功后系统分配「寄存/兑奖端口号」，参会人凭端口号到服务台领取物料；
3. 抽奖只由管理端发起，大屏被动轮询展示，不提供任何写接口；
4. 工作人员在管理端核验身份并发放奖品/权益，所有动作留操作日志。

## 6. 已知安全控制（请勿作为漏洞重复提交）

1. 列表接口不返回完整手机号/邮箱，属**有意脱敏**；
2. 大屏匿名接口只返回端口号、奖项、时间，**不返回姓名与手机号**，属有意设计；
3. 签到成功后**禁止修改手机号**，用于防止顶替签到；
4. 员工相关接口有岗位白名单（`StaffRoleGuard`），非授权岗位返回 403 属预期；
5. 限流只信任 nginx 写入的 `X-Real-IP`，伪造该请求头不会绕过限流；
6. 赠票系统对未知邮箱返回与已知邮箱**相同的提示，但不实际发信**，是防账号枚举设计；
7. 抽奖、清场、恢复、作废等写操作只能由管理端发起，大屏与 H5 无对应端点；
8. 旧路径 301 到 `/kconluck2026/`，目标固定，不是开放重定向；
9. 管理端导出/导入接口对文件大小、行数、字段长度有上限校验，超限返回业务错误而非 500；
10. **官网侧**：后端只在「来源是本机 + 携带 nginx 注入的私有令牌 `X-Kcon-Proxy-Token`」时才采信 `X-Real-IP`，外部伪造该头不影响限流分桶；`/kcon_mcp_server/`、`/.env`、`/app.py`、`/deploy/` 等路径由 nginx 直接 404，投稿/反馈 JSON 不走 web 根下载。

## 11. 会议官网 + MCP 后端（新增组件）

### 11.1 这是什么

KCon 会议官网（静态站）+ 一个 Flask 后端（议题投稿、反馈收集），外加一个 **MCP 服务**让 AI 客户端（Claude/Trae 等）也能调用投稿与反馈。它与 §1–§10 的主系统**代码、数据库、nginx 完全独立**，只是恰好部署在同一台机器。

- 网站入口：`http://123.57.9.62:8090/`（历届页 `/kcon2021.html`…`/kcon2024.html`、`/history.html`）
- 代码位置：服务器 `/opt/kcon2026/`，后端在 `/opt/kcon2026/kcon_mcp_server/`
- 服务：systemd `kcon-mcp.service`（gunicorn，仅监听 `127.0.0.1:5001`，公网不可直连）+ 宿主机 nginx（`/etc/nginx/conf.d/kcon.conf`）

### 11.2 HTTP 攻击面（8090）

| 端点 | 方法 | 说明 |
|---|---|---|
| `/api/conference`、`/api/history` | GET | 只读，返回会议/历届 JSON |
| `/api/submit-topic` | POST | 议题投稿：title/abstract/speaker_name/speaker_email/speaker_phone/speaker_bio/tags/duration |
| `/api/feedback` | POST | 反馈：content/category/contact |

已有控制（测到同类行为勿重复报）：

- 匿名可用，但**双层限流**：应用层按真实 IP 每分钟 3 次，nginx 层 `12r/m`（burst 5）兜底；另有按邮箱的日配额；
- 请求体上限 64 KB（超出返回 **413**）；所有字符串字段有长度上限；邮箱有格式校验；
- `duration` 要求 1–180 的整数，**越界或类型不对时静默回落为 20 而不是报错**——这是设计，不按「参数校验缺失」报；
- `X-Real-IP` 采信规则见 §6 第 10 条——**从公网伪造该头绕不过限流**；
- 敏感路径（`.env`、`app.py`、`server.py`、`deploy/`、`kcon_mcp_server/`、`.git`）nginx 直接 404（已实测）；
- 静态资源 handler 有目录穿越防护（resolve 后必须仍在 web 根内）。

值得重点试的方向（不限于）：投稿内容存储后在前端渲染是否有 XSS 路径、限流窗口的边界竞争、邮箱配额绕过、超长/非法类型参数引起的异常行为。

### 11.3 MCP 服务（stdio，无网络端口）

`server.py` 提供 4 个工具：`get_conference_info`、`get_history`（只读）；`submit_topic`、`submit_feedback`（写盘）。

- 它**不监听任何端口**，由 AI 客户端以子进程拉起，走 stdin/stdout 的 JSON-RPC。**对它做端口扫描、网络协议攻击不适用，不算漏洞也不必有 findings**；
- 主机上有现成 venv：SSH 登录后 `/opt/kcon2026/kcon_mcp_server/.venv/bin/python /opt/kcon2026/kcon_mcp_server/server.py` 即可起一个实例本地 fuzz（只读核查权限内允许跑进程，但**不得改配置/重启服务**）；
- 它的写盘落点：`/opt/kcon2026/kcon_mcp_server/submissions/`、`feedback/`（每提交一个 JSON 文件，文件名含 UUID）。测试产生的文件请在结束前清掉；
- 入参校验与 HTTP 侧同源（长度/邮箱/duration/category 白名单），非法输入应返回结构化中文错误、进程不崩。如果 fuzz 中发现**任何一条输入让进程退出或产生 traceback 输出到 stdout 之外的副作用**，算 bug，优先报。

### 11.4 官网侧的额外禁令

- 不要试图猜/爆破 `X-Kcon-Proxy-Token` 的值（32 字节随机数，且它只影响限流分桶，拿到也仅是正常绕过限流的手段之一，属已知设计而非入口）；
- 不要删除或改写 `/opt/kcon2026/` 下任何文件（含 submissions/feedback 里别人提交的样例）；
- 官网数据目录里的 `conference.json`/`history.json` 是站点内容源，只读。
