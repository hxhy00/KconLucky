# KCon 2026 签到 + 抽奖系统 · 部署运行

**版本**：v4.0（Docker Compose + 公网服务器）
**日期**：2026-10-22
**部署方案**：**Docker Compose 一键编排，部署在公网云服务器**
**目标环境**：云服务器（Linux x86_64，2G 内存），观众手机经公网访问
**已移除**：原「会前打包 → 现场离线笔记本运行」方案（2026-10-22 确认不再保留）
**部署实例**：`123.57.9.62`

---

## 1. 方案总览

一句话：**一套镜像 + 一份编排**，跑在公网云服务器上，观众手机直接经公网访问。

```
【本地开发机 · 联网】                     【公网服务器 · Linux x86_64】
 改代码 → docker buildx build --platform linux/amd64
      → docker save | ssh | docker load  ──►  docker compose up -d
                                              ↓
                    观众手机（任意网络）→ 扫码 http://<服务器IP>/sign 自助签到
                    签到台水牌二维码 → 观众截图 → 工作人员发胸牌
                    笔记本 HDMI → 浏览器打开 /screen/ 投屏（抽奖）
```

**为什么是公网而不是现场离线**（2026-10-22 决策）：

| 维度 | 公网服务器（现状） |
|---|---|
| 观众接入 | 任意网络可达，**不依赖会场 WiFi 质量**，无需实测 AP 隔离/带机量 |
| 现场风险 | 只剩「会场到服务器的公网质量」，不再有热点带机量 8–20 台上的硬上限 |
| 运维成本 | 需维护服务器、监控内存与磁盘、注意备案与安全基线 |
| 数据位置 | 名单与签到数据在云端，需关注隐私合规（见第 13 节） |

> **关键概念：本地构建，服务器只 `load` 与启动。** 服务器上不跑 `mvn` / `npm`，也不拉基础镜像（出网受限）。
> 本地为 Apple Silicon 时必须显式 `--platform linux/amd64`，否则 `load` 上去是 arm 镜像，起不来。

## 2. 架构

```
                     ┌──────────────────────────────────────────┐
   观众手机  ──────► │  nginx-web 容器（前端总入口 :80）          │
   （自助扫码 · 公网）│   /            → 入口分流页（选入口）      │
                     │   /admin/      → 管理端（静态）            │
                     │   /screen/     → 抽奖大屏（静态）          │
                     │   /sign/       → 签到 H5（静态）           │
                     │   /prod-api/   → 反向代理到 backend:8080   │
                     └───────────────┬──────────────────────────┘
                                     │ 容器内网络
                                     ▼
                     ┌──────────────────────────┐      ┌────────────────────────┐
   现场笔记本 ─────► │  backend 容器（:8080）    │─────►│  mysql 容器（:3306）    │
   HDMI 投大屏       │  RuoYi-Vue 后端 jar       │ JDBC │  volume → ./data/mysql │
   （只开浏览器）     └──────────────────────────┘      └────────────────────────┘
                                                                       │
                                                          ./data/mysql 持久化目录
```

**关键点**
- 只有 `nginx-web` 对外暴露 80 端口，**观众用自己的手机**扫码，经公网访问 `http://<服务器IP>/sign/`。
- 根路径 `/` 是**入口分流页**（列出管理端 / 大屏 / 签到三个入口），不是签到页；签到页固定在 `/sign/`，避免误把签到页当管理端打开。
- 三端前端共用同一个后端域名与端口，**不存在跨域问题**（同源 `/prod-api/` 反代）。
- MySQL 不对外暴露端口（`127.0.0.1:3307:3306` 仅绑本机调试用，可关闭），避免公网误连。
- 现场笔记本**不再跑容器**，只开浏览器投屏 `/screen/`；抽奖与兑奖在管理端网页上操作，数据在服务器。

> **内存基线（重要）**：服务器总内存仅 1.7G 且**无 swap**。JVM 堆必须压住，
> 当前为 `-Xmx512m -XX:MaxMetaspaceSize=192m`，见 6.1。堆设大到 768m 会导致
> JVM + MySQL + 系统进程合计触顶，被内核 OOM Kill。

```dotenv
# 生成方式：openssl rand -base64 48
# 后端启动时会校验，不达标直接拒绝启动（避免配漏了却在现场裸奔）
TOKEN_SECRET=<用 openssl rand -base64 48 生成>

# ---- 现场信息（用于生成签到二维码与展示地址）----

```

> **`TOKEN_SECRET` 是必填项**：`.env` 里没有它，`docker compose up` 会直接报错并提示，
> 这是刻意设计——不留「忘配就用弱默认值」的口子。

### 4.0 `LAN_IP` 的填法

变量名沿用历史命名（未改名以免影响已有 `.env`），实际含义是**对外访问地址**：

| 部署形态 | `LAN_IP` 填什么 | 观众手机的前提 |
|---|---|---|
| 公网服务器（当前） | 公网 IP 或域名，如 `123.57.9.62` | **只要能上网即可**，无需同一网络 |
| 内网/笔记本（已不采用） | 本机局域网 IP，如 `192.168.1.100` | 与笔记本同一 WiFi / 同一网段 |

管理端数据总览的提示文案已通用化，不写死「同一局域网」。

> 公网部署还应补 HTTPS（见第 15 节）：签到页要提交手机号，明文 HTTP 不可接受。
> 上了域名后二维码会自动变成 `https://kcon.example.com/sign/`。
> **当前线上实例仍是明文 HTTP**，属于已知未完成项，见 15.2。

### 4.1 管理端部署基路径（三处必须一致）

管理端挂在 `/admin/` 子路径下，以下三处都写 `/admin/`：

| 位置 | 配置项 | 值 |
|---|---|---|
| `ruoyi-ui/.env.production` / `.env.staging` | `VUE_APP_BASE_PATH` | `/admin/` |
| `ruoyi-ui/.env.development` | `VUE_APP_BASE_PATH` | `/` |
| `ruoyi-ui/vue.config.js` | `publicPath` | 取 `VUE_APP_BASE_PATH`，不另行硬编码 |
| `docker/web/nginx.conf` | `location /admin/` | `/admin/` |

`VUE_APP_BASE_PATH` 是**唯一来源**，有三个用途：vue-router 的 `base`（决定路由 path 与实际 URL 的对应关系）、
`vue.config.js` 的 `publicPath`（静态资源前缀）、以及 `location.href` 硬跳转的路径前缀。
缺 base 会导致刷新或直接访问子页面时路径错位。

> 值**必须以 `/` 结尾**。`vue.config.js` 已加构建期断言，配错会在 `npm run build` 阶段直接报错，
> 不会带着错误配置构建出包。

> TOKEN_SECRET、mem_limit/logging/web-static 卷等，未随版本同步更新）。

```yaml
services:
  mysql:
    image: mysql:8.0
    container_name: kcon-mysql
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD}

      - ./sql/00-ry-base.sql:/docker-entrypoint-initdb.d/00-ry-base.sql:ro

    ports:
      - "127.0.0.1:${MYSQL_DEBUG_PORT:-3307}:3306"   # 仅本机调试，不对公网暴露
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "127.0.0.1", "-p${MYSQL_ROOT_PASSWORD}"]
      interval: 5s
      timeout: 3s
      retries: 20
    networks: [kcon]

  backend:
    build:
      context: .                          # 项目根：镜像需要同时拷 docker/ 与 ruoyi/
      dockerfile: docker/backend/Dockerfile
    image: kcon/backend:1.0
    container_name: kcon-backend
    restart: unless-stopped
    environment:
      TZ: ${TZ:-Asia/Shanghai}
      BACKEND_PORT: 8080
      # 会覆盖 Dockerfile 的 ENV，改 JVM 参数改这里（或 .env），见 6.1
      JAVA_OPTS: ${JAVA_OPTS:--Xms256m -Xmx512m -XX:MaxMetaspaceSize=192m -XX:+ExitOnOutOfMemoryError}
      SPRING_DATASOURCE_DRUID_MASTER_URL: jdbc:mysql://mysql:3306/${MYSQL_DATABASE:-kcon_lucky}?useUnicode=true&characterEncoding=utf8&zeroDateTimeBehavior=convertToNull&useSSL=false&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true
      SPRING_DATASOURCE_DRUID_MASTER_USERNAME: root
      SPRING_DATASOURCE_DRUID_MASTER_PASSWORD: ${MYSQL_ROOT_PASSWORD:?}
      REDIS_HOST: redis
      REDIS_PORT: 6379
    depends_on:
      mysql:
        condition: service_healthy
    networks: [kcon]

  web:
    build:
      context: .
      dockerfile: docker/web/Dockerfile
      args:
        LAN_IP: ${LAN_IP}
    image: kcon/web:1.0
    container_name: kcon-web
    restart: unless-stopped
    ports:
      - "${WEB_PORT:-80}:80"
    depends_on: [backend]
    networks: [kcon]

networks:
  kcon:
    driver: bridge
```

> **配置外置**：后端不打包任何数据库地址，全部通过 `SPRING_DATASOURCE_*` 环境变量注入，
> 满足「配置集中、不硬编码」要求（见 01-需求规格 11.4）。

## 6. Dockerfile

### 6.1 `docker/backend/Dockerfile`（多阶段构建）

```dockerfile
# --- 构建阶段 ---
FROM maven:3.9-eclipse-temurin-17 AS build
WORKDIR /src

# Maven 国内镜像（由 compose 以 build context=项目根 + dockerfile 指定，见下方 COPY 说明）
COPY docker/maven-settings.xml /root/.m2/settings.xml

# 先拷 pom，利用 Docker 层缓存加速依赖下载
COPY ruoyi/pom.xml ./
COPY ruoyi/ruoyi-admin/pom.xml ruoyi-admin/
COPY ruoyi/ruoyi-common/pom.xml ruoyi-common/
COPY ruoyi/ruoyi-framework/pom.xml ruoyi-framework/
COPY ruoyi/ruoyi-system/pom.xml ruoyi-system/
COPY ruoyi/ruoyi-quartz/pom.xml ruoyi-quartz/
COPY ruoyi/ruoyi-generator/pom.xml ruoyi-generator/
RUN mvn -B dependency:go-offline -DskipTests

COPY ruoyi/ .
RUN mvn -B clean package -DskipTests

# --- 运行阶段 ---
FROM eclipse-temurin:17-jre
WORKDIR /app

# 堆上限按宿主机总内存定：线上 1.7G 无 swap，768m 会 OOM
ENV TZ=Asia/Shanghai JAVA_OPTS="-Xms256m -Xmx512m -XX:MaxMetaspaceSize=192m -XX:+ExitOnOutOfMemoryError"

# mysql-client：管理端「数据迁移」功能需要调 mysqldump / mysql（需求 AC-11）
RUN set -eux; \
    apt-get update; \
    apt-get install -y --no-install-recommends mysql-client; \
    rm -rf /var/lib/apt/lists/*

COPY --from=build /src/ruoyi-admin/target/ruoyi-admin.jar app.jar
EXPOSE 8080
ENTRYPOINT ["sh", "-c", "java $JAVA_OPTS -jar app.jar"]
```

> **`JAVA_OPTS` 有两处，改的时候当心**：Dockerfile 里的 `ENV` 会被
> `docker-compose.yml` 的 `environment.JAVA_OPTS` **覆盖**。只改 Dockerfile 不生效。
> compose 里写的是 `${JAVA_OPTS:-<-Xmx512m 默认值>}`，两处默认值需保持一致；
> 临时调参改 `.env` 即可。
>
> **`-XX:+ExitOnOutOfMemoryError`** 是刻意加的：内存不足时让进程立即退出、由
> `restart: unless-stopped` 拉起，而不是卡在半死不活的状态。宁可短暂 502 也不要长时间不应答。

`docker/maven-settings.xml` 用阿里云镜像（国内源）：

```xml
<mirror>
  <id>aliyun</id>
  <mirrorOf>*</mirrorOf>
  <url>https://maven.aliyun.com/repository/public</url>
</mirror>
```

### 6.2 `docker/web/Dockerfile`（三端统一构建 + Nginx）

> ⚠️ **以下为历史示意，实际以 `docker/web/Dockerfile` 为准**（现版为三个独立 build stage、
> 独立 nginx.conf/entrypoint.sh/web-static 卷发布机制，且 `ARG LAN_IP` 已不存在）。

```dockerfile
# --- 三端依次构建 ---
FROM node:20-alpine AS build
ARG LAN_IP=127.0.0.1
WORKDIR /src
COPY ruoyi-ui/package*.json ruoyi-ui/
RUN cd ruoyi-ui && npm config set registry https://registry.npmmirror.com && npm ci
COPY ruoyi-ui/ ruoyi-ui/
RUN cd ruoyi-ui && npm run build:prod

COPY checkin-h5/package*.json checkin-h5/
RUN cd checkin-h5 && npm config set registry https://registry.npmmirror.com && npm ci
COPY checkin-h5/ checkin-h5/
RUN cd checkin-h5 && npm run build

COPY screen/package*.json screen/
RUN cd screen && npm config set registry https://registry.npmmirror.com && npm ci
COPY screen/ screen/
RUN cd screen && npm run build

# --- 运行阶段 ---
FROM nginx:1.27-alpine
COPY docker/web/nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /src/ruoyi-ui/dist     /usr/share/nginx/html/admin
COPY --from=build /src/checkin-h5/dist   /usr/share/nginx/html/checkin
COPY --from=build /src/screen/dist       /usr/share/nginx/html/screen
EXPOSE 80
```

### 6.3 `docker/web/nginx.conf`

```nginx
server {
    listen 80;
    server_name _;
    client_max_body_size 20m;          # 名单 Excel 上传

    # 根路径：入口分流页（管理端 / 大屏 / 签到）
    location = / { root /usr/share/nginx/html; try_files /index.html =404; }
    location = /index.html { root /usr/share/nginx/html; }   # index/try_files 会内部跳转到此，必须单列

    # 签到 H5：观众入口。必须 = /sign + ^~ /sign/ 两段式，
    # 单一 location /sign 是前缀匹配，会把 /signup、/signin 也吞进来
    location = /sign { return 301 /sign/; }
    location ^~ /sign/ { alias /usr/share/nginx/html/checkin/; index index.html; try_files $uri $uri/ /sign/index.html; }

    # 管理端 / 抽奖大屏：无尾斜杠入口统一 301
    location = /admin  { return 301 /admin/; }
    location = /screen { return 301 /screen/; }
    location /admin/  { alias /usr/share/nginx/html/admin/;  index index.html; try_files $uri $uri/ /admin/index.html; }
    location /screen/ { alias /usr/share/nginx/html/screen/; index index.html; try_files $uri $uri/ /screen/index.html; }

    # 兜底：nginx 镜像内没有 /etc/nginx/html，落到默认 location 会变成 nginx 硬 404 页
    location / { return 404; }

    # 后端反向代理（同源，天然无跨域）
    location /prod-api/ {
        proxy_pass http://backend:8080/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_read_timeout 60s;
    }
}
```

> 三端前端的构建 `base` 需分别配为 `/admin/`、`/screen/`、`/sign/`，接口基址统一为 `/prod-api`。
> 实际生效的配置以 `docker/web/nginx.conf` 为准，本节只作说明用。

## 7. 日常使用

> 所有命令在**服务器**上执行（`ssh root@123.57.9.62` 后 `cd /root/Code/kcon-lucky`）。
> 镜像由本地构建后 `load` 进去，服务器上**不要**执行 `--build`（出网受限，拉不到基础镜像）。

```bash
cd /root/Code/kcon-lucky

# 启动 / 更新（改了镜像后）
docker compose up -d --no-build

# 改了 environment（如 JAVA_OPTS）必须 force-recreate，否则环境变量不更新
docker compose up -d --no-build --force-recreate backend

# 查看状态与日志
docker compose ps
docker compose logs -f backend

# 停止（保留数据）
docker compose down

# 重启单个服务
docker compose restart backend
```

**四个坑**

- `.env` 不在 git 里（服务器本地生成，含数据库口令与 `TOKEN_SECRET`）。`git pull` 不会碰它，但**不要**执行 `git checkout .` / `git clean -fd` 清理工作区，会把配置抹掉。
- `sql/` 下的初始化脚本**只在数据卷为空时执行一次**。已部署的库不会重跑，本次若改了建表或初始化数据，须按 9.3 手工执行迁移。
- 服务器出网无法直连 Docker Hub（实测 30s 超时，DaoCloud 镜像源返回 502），已在 `/etc/docker/daemon.json` 配 `docker.1panel.live` 加速。**换机器部署必须重配这一项**，否则构建第一步就拉不到镜像。
- 服务器统一用 `--no-build` 启动（镜像由本地构建后 load）；`--build` 只重建 `backend` 与 `web`，且在服务器上执行会因拉不到基础镜像而失败。`mysql`/`redis` 是拉取的镜像，不参与构建。
- 本次改动涉及数据或配置变更时，更新前先跑 9.1 的备份。
- **换版 404 防护（第三轮测试报告问题 5）**：三端静态资源持久化在宿主机 `data/web-static/` 卷。web 容器每次启动时按「合并」方式发布新版（hash 文件名不冲突，上一版 chunk 自然留存），并用清单把更早版本的孤儿文件回收，卷内始终只保留两代资源。已打开的旧页面（缓存着旧 `index.html`）刷新时仍能拿到旧 hash 资源，不再 404 白屏。**不要手工清理 `data/web-static/`**；如需强制全量重置，停 web 后删掉该目录再 `up -d web` 即可（入口 HTML 均为 no-cache，不受影响）。

### 7.2 改账号 / 改口令后强制旧会话下线

RuoYi 的登录 token 存在 Redis（`login_tokens:*`）且**携带 `userName`**。
只改 `sys_user` 的话，改名前签发的 token 在到期前仍然可用——等于改口令没生效。
所以改账号名或改口令后，必须清一次登录态：

```bash
cd /root/Code/kcon-lucky
# 精确匹配 login_tokens 前缀，不用 FLUSHDB：后者会连带清掉参数与字典缓存
docker compose exec -T redis redis-cli --scan --pattern 'login_tokens:*' \
  | xargs -r -n 200 docker compose exec -T redis redis-cli DEL
```

> 改口令本身**不要手写 SQL 存哈希**：本项目口令是 BCrypt（`SecurityUtils.encryptPassword`
> 用 `BCryptPasswordEncoder`），手算极易算错。走应用自身的接口即可，登录后调用：
> `PUT /system/user/profile/updatePwd`，body 为 `{"oldPassword":"旧口令","newPassword":"新口令"}`。
> 改账号名没有界面入口，只能 `update sys_user set user_name=...`。

### 7.3 Git 分支模型（Git Flow）

| 分支 | 用途 | 来源 / 合入 |
|---|---|---|
| `main` | 只存放已发布版本 | **唯一来源**是 `release/*` 与 `hotfix/*`；**禁止直接 commit、禁止直接 push**，`develop` 与 `feature/*` 均不得直接合入 |
| `develop` | 日常集成分支 | `feature/*` 以 `--no-ff` 合入；由 `main` 的初始 commit 切出，长期存在 |
| `feature/<seq>-<主题>` | 功能 / 缺陷 / 重构 / 文档开发 | 从 `develop` 切出，`--no-ff` 合回 `develop`，完成后删除 |
| `release/<版本>` | 发布冻结与回归 | 从 `develop` 切出；冻结期只收 bugfix，修复须回合 `develop`；合入 `main` 时打 tag，发版后删除 |
| `hotfix/<seq>-<主题>` | 线上紧急修复 | 从 `main` 切出，**双向**合回 `main` 与 `develop`，并打 tag |

- **`main` 分支保护必配**：禁止直接 push、禁止直接 commit、限定合并来源为 `release/*` 与 `hotfix/*`。规则文本与平台配置二者缺一不可。
- 分支命名同时满足 `.specify/branch-convention.yml` 的 `{type}/{seq}-{kebab}`，`main` / `develop` 是基线分支，不参与命名校验。
- 一个 spec 完成（代码 + 文档 + 验证通过）后合并到 `develop`，并按 **spec 粒度**推送。
- agent 可以执行本地 `merge --no-ff`；`git push` 一律由用户手动执行。

> 完整约束、分支保护检查清单与发布 / 热修命令见 [`CONTRIBUTING.md`](../CONTRIBUTING.md)。

### 7.4 版本发布（手动）

> 2026-10-22 起**不再使用 CD**：Gitee 的 Tag Push WebHook 已撤销，仓库中的 webhook 接收器、
> systemd 服务、`scripts/deploy.sh` 与 nginx 的 `/hooks/deploy` 反代均已移除。
> 发布改由本地构建镜像后手工推送到服务器，完整命令见第 8 节。

**发布顺序**

1. 本地 `docker buildx build --platform linux/amd64` 构建 backend / web 镜像（改了哪端构建哪端）
2. `docker save | gzip | ssh | docker load` 推到服务器
3. `rsync` 同步 `docker-compose.yml`、`sql/`（有变更时）；基线 SQL 有变更时按 9.3 重建库
4. 服务器 `docker compose up -d --no-build`；改了 `environment`（如 `JAVA_OPTS`）时加 `--force-recreate`
5. 按 8.3 做三端健康检查

**回滚**

镜像 tag 固定为 `kcon/backend:1.0` / `kcon/web:1.0`，本地保留上一版镜像即可回滚：
重新 `docker save` 旧镜像 → `load` → `up -d --force-recreate`。
若涉及数据库，回滚前先用「数据迁移」导出当前数据。

**边界**

- 迁移只保证向前幂等，不提供自动回滚；涉及破坏性 DDL 的发布仍需先备份。
- 发布过程没有自动化编排，步骤必须按顺序人工执行；发布后务必做 8.3 的验证。

> **赠票系统（gift）已于 2026-10-27 移除**：会前赠票分发改用腾讯问卷 + 人工整理，
> 名单仍由本系统「参会名单 → 导入」承接。历史数据与代码见归档标签 `archive/020-gift-system-merge`。

## 8. 部署到公网服务器（核心流程）

服务器出网受限（无法直连 Docker Hub），因此**镜像在本地构建、以 tar 推送到服务器 `load`**，服务器只负责启动。

### 8.1 本地构建（注意 CPU 架构）

```bash
cd KconLucky

# Apple Silicon 必须显式指定 amd64，否则产物是 arm 镜像，服务器上起不来
docker buildx build --platform linux/amd64 \
  -f docker/backend/Dockerfile -t kcon/backend:1.0 --load .

docker buildx build --platform linux/amd64 \
  -f docker/web/Dockerfile -t kcon/web:1.0 --load .
```

### 8.2 推送并启动

```bash
# 传镜像（压缩后再传，省带宽）
docker save kcon/backend:1.0 | gzip -1 | ssh <server> 'gunzip | docker load'
docker save kcon/web:1.0     | gzip -1 | ssh <server> 'gunzip | docker load'

# 传编排与配置（.env 是 untracked，首次需手工放）
rsync -az docker-compose.yml <server>:/root/Code/kcon-lucky/

# 启动
ssh <server> 'cd /root/Code/kcon-lucky && docker compose up -d --no-build'
```

> **必须用 `--force-recreate` 的场景**：改了 `docker-compose.yml` 里的 `environment`
> （如 `JAVA_OPTS`）或镜像内 `ENV` 时。`up -d` 会复用已有容器，**环境变量不会更新**，
> 表现为「明明改了却还是旧参数」。此时用 `docker compose up -d --force-recreate backend`。

### 8.3 验证

```bash
ssh <server> 'cd /root/Code/kcon-lucky && docker compose ps'
for p in / /admin/ /sign/ /screen/; do
  printf "%-10s %s\n" "$p" "$(curl -s -o /dev/null -w '%{http_code}' http://<server>$p)"
done
curl -s http://<server>/prod-api/captchaImage     # 应返回 JSON
```

四个路径均需 200，后端接口返回 `{"msg":"操作成功","code":200,...}`。

- 现场笔记本只开浏览器，**不需要装 Docker**；大屏分辨率与输出设置在笔记本侧调整。

### 8.5 备选：走内网 Harbor 镜像仓库（后续迭代推荐）

内网 Harbor 地址 `registry.k8s.intra.knownsec.com`，Harbor 项目为 `kcon`。
办公网与服务器都能直连，**镜像构建一次、推送一次**，后续更新只换 `image:` 的 tag/digest，
不再走 `docker save | ssh | docker load`。

**命名与标签约定**

| 镜像 | 仓库路径 | 标签 |
|---|---|---|
| 后端（Spring Boot） | `kcon/kcon2026/kconlucky-backend` | `rc`（最新）+ `rc-<git短SHA>`（可回溯） |
| 前端 + nginx | `kcon/kcon2026/kconlucky-web` | 同上 |

完整地址示例：`registry.k8s.intra.knownsec.com/kcon/kcon2026/kconlucky-backend:rc`

> Harbor 项目是 `kcon`，`kcon2026/kconlucky-*` 是项目内的仓库子路径；最终路径以部署侧确认为准。

**前置条件（仅首次）**

1. 账号必须是 `kcon` 项目成员，且角色至少 `maintainer`（才有 push 权限）；
2. 本机 Docker 要信任公司 CA（否则报 `x509: certificate signed by unknown authority`）：
   从 macOS 钥匙串导出 `Knownsec RSA SERVER CA` 与 `Knownsec RSA Certification Authority`
   （两张证书按顺序拼接）到 `~/.docker/certs.d/registry.k8s.intra.knownsec.com/ca.crt`，然后重启 Docker 引擎；
3. 登录一次，口令走 stdin，不写进任何文件：
   `printf '%s' '<口令>' | docker login registry.k8s.intra.knownsec.com -u <账号> --password-stdin`。

**构建并推送（必须 linux/amd64）**

```bash
TAG=rc-$(git rev-parse --short HEAD)
REG=registry.k8s.intra.knownsec.com/kcon/kcon2026

docker buildx build --platform linux/amd64 -f docker/backend/Dockerfile \
  -t $REG/kconlucky-backend:rc -t $REG/kconlucky-backend:$TAG --push .

docker buildx build --platform linux/amd64 -f docker/web/Dockerfile \
  -t $REG/kconlucky-web:rc -t $REG/kconlucky-web:$TAG --push .
```

**交付给部署侧：用 digest（镜像 ID）锁定**

```bash
docker buildx imagetools inspect $REG/kconlucky-backend:$TAG | grep Digest
docker buildx imagetools inspect $REG/kconlucky-web:$TAG     | grep Digest
```

`docker-compose.yml` 里改成 digest，避免 `rc` 被覆盖后被动升级：

```yaml
services:
  backend:
    image: registry.k8s.intra.knownsec.com/kcon/kcon2026/kconlucky-backend@sha256:<digest>
  web:
    image: registry.k8s.intra.knownsec.com/kcon/kcon2026/kconlucky-web@sha256:<digest>
```

**服务器更新 / 回滚**

```bash
cd /root/Code/kcon-lucky
docker compose pull          # 按 compose 里的 tag/digest 拉取
docker compose up -d --no-build --force-recreate
docker compose ps            # 四容器 Up，mysql/redis healthy
```

回滚：把两份 `image:` 换回上一个 `rc-<sha>` 的 digest，重复上面两条命令。
`rc` 标签用于「跟最新」，`rc-<sha>` 用于「精确回滚」，两者同时打，不要只打 `rc`。

> `.env` 仍只存在于服务器（untracked），**不进镜像、不进仓库**；
> 镜像里只有代码与构建产物，任何口令、密钥都通过环境变量注入。

### 9.2 恢复

```bash
docker compose exec -T mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" < data/backup/xxx.sql
```

### 9.3 数据库重建（无迁移脚本模式）

**增量迁移脚本已于 2026-10-23 全部废弃删除**：所有表结构、菜单、角色、授权均已吸收进基线三脚本
（`00-ry-base.sql` → `kcon_lucky.sql` → `kcon_menu.sql`），`initdb` 首次启动自动执行，
不依赖任何迁移。

**库结构变更后的升级方式**（当前无生产数据，直接重建）：

```bash
docker compose down
rm -rf data/mysql          # 彻底清空数据卷（有要保留的数据先走 9.1 备份）
docker compose up -d       # initdb 重新执行基线三脚本
```

> **基线账号**：`staff` 由 `kcon_menu.sql` 创建，**默认停用**（口令是仓库里的公开已知值）。
> 启用方式：超管登录 →「设置 → 用户管理」→ 重置密码 → 启用。
> 现场账号不要沿用仓库里的初始口令；工作人员也无法自助改密，改密只能由超管操作。

> **改了 `sql/` 下的菜单或表结构**：直接改基线三脚本，然后按上面步骤重建库验证；
> 本项目当前阶段（会前）无存量数据需要保护，不维护迁移脚本。

> **用 mysqldump 备份恢复会覆盖 `sys_role` / `sys_user` 等系统表**。
> 从旧备份恢复后，备份之后新建的角色、账号、授权会一并消失，如结构有变需重建基线补齐。

### 9.4 清空测试数据（开场前重置，名单也会被清空）

## 12. 故障排查

| 现象 | 排查 |
|---|---|
| `web` 起不来，80 被占 | `lsof -i:80`；改 `.env` 的 `WEB_PORT` |
| `backend` 反复重启 | `docker compose logs backend`；多为 MySQL 未就绪，看 healthcheck 是否通过 |
| 登录后先跳 404，点返回才进管理端 | 静态 `redirect` 指向了动态路由。动态路由要等 `GenerateRoutes` 才注册，`redirect` 在 `beforeEach` 之前解析必然落进 404。`router/index.js` 里 `/` 的 `redirect` 只能是静态路由（本项目为 `'index'`） |
| 刷新页面后样式丢失或跳分流页 | 管理端 vue-router 没配 `base`。`ruoyi-ui/.env.production` 的 `VUE_APP_BASE_PATH` 须为 `/admin/`，与 `vue.config.js` 的 `publicPath`、`nginx` 的 `location /admin/` 三处一致 |
| 退出登录后跳到根路径分流页 | `location.href` 硬跳转未带 base。`request.js`、`Navbar.vue` 里应拼 `process.env.VUE_APP_BASE_PATH`，不能写死 `/index` |
| 打开 `http://<IP>/` 却是签到页 | 镜像版本旧（v3.2 及以前根路径就是签到页）。在本地重建 web 镜像并 `docker save \| ssh \| docker load` 推到服务器，再 `docker compose up -d --no-build web`；新版本根路径为分流页，签到页在 `/sign` |
| 管理端菜单出现「系统管理/系统监控/若依官网」 | `sql/kcon_menu.sql` 未重新导入。用 `scripts/` 下的菜单初始化方式重跑，或执行该文件中的 `UPDATE sys_menu SET visible='1' WHERE menu_id IN ('1','2','3','4','5')` |
| 观众扫码打不开 | 服务器 80 端口是否放行（云厂商安全组）、`curl -I http://<公网IP>/sign/` 是否 200；内网隔离场景才需考虑同网段问题 |
| 二维码指向 `127.0.0.1` | `.env` 的 `LAN_IP` 未填或未生效（手机扫到的是手机自己的 127.0.0.1）。改 `.env` 后 `docker compose up -d --force-recreate backend` |
| 签到页空白、控制台报资源 404 | 签到 H5 的 `base` 与 nginx 路径不一致。`checkin-h5/vite.config.js` 须为 `base: '/sign/'`，nginx 须有 `location ^~ /sign/`；资源实际从 `/sign/assets/*` 取，**不需要**为 `/assets/` 单独配规则 |
| 打开 `/admin` 或 `/screen`（漏尾斜杠）是 nginx 错误页 | 镜像内没有 `/etc/nginx/html`，落到默认 location 就是 nginx 硬 404。已配 `location = /admin { return 301 /admin/; }`，若出现说明 nginx 配置被改动过 |
| `/signup`、`/signin` 之类的路径返回了签到页 | `location /sign` 是前缀匹配，会吞掉所有同前缀路径。必须用 `location = /sign` + `location ^~ /sign/` 两段式 |
| 构建报「VUE_APP_BASE_PATH 必须以 / 结尾」 | `.env.production` / `.env.staging` 里的 `VUE_APP_BASE_PATH` 少了尾部斜杠。这是构建期断言，属于预期行为 |
| 后端起不来，日志报 `token.secret 未配置或强度不足` | `.env` 缺 `TOKEN_SECRET`，或值不足 32 字节 / 用了若依开源默认值。执行 `openssl rand -base64 48` 生成后写入 `.env`。这是刻意的拒绝启动，不是 bug |
| `docker compose up` 报 `必须在 .env 中配置 TOKEN_SECRET` | 同上，compose 层的必填校验先于容器启动拦下了 |
| 大屏抽奖返回「访问过于频繁」 | 触发了 `@RateLimiter(10秒20次)`。正常现场操作（数秒一次）不会触发；若确实需要更高上限，调大 `DrawScreenController` 上的 `count` |
| 管理端菜单里出现了系统管理等原生菜单 | 只执行了菜单 SQL 的 INSERT 部分。需确认 `kcon_menu.sql` 完整执行（含隐藏原生菜单 + 收回普通角色授权） |
| 用 `ry` 账号登录提示用户不存在 | 预期行为。`ry` 是 RuoYi 自带测试账号，已从基线 `sql/00-ry-base.sql` 删除。现场只用 `KconLucky` 与工作人员账号 |
| 签到页能开但接口 502 | `backend` 未起或 nginx 反代路径不对（检查 `/prod-api/` 末尾斜杠） |
| 端口号重复 | 查 `kcon_port_pool` 是否存在重复 `port_no`（应为 PK，不可能重复）；确认未被手工改库 |
| `docker compose up` 报拉不到镜像 | 服务器出网受限，误触发了 build/pull。应在本地 `buildx --platform linux/amd64` 构建后 `docker save | ssh | docker load`，再 `up -d --no-build` |
| 构建时依赖拉不动 | 构建只在**本地开发机**执行；已配阿里云 / npmmirror 国内源 |
| `docker load` 后容器起不来（exec format error） | 镜像架构不符。本地 Apple Silicon 必须 `--platform linux/amd64` 构建，否则产物是 arm64，服务器 x86 上起不来 |
| 改了 `JAVA_OPTS` 但容器内还是旧值 | `up -d` 复用已有容器，环境变量不刷新。用 `docker compose up -d --force-recreate backend`，并确认改的是 `docker-compose.yml` 而非只改 Dockerfile |
| 后端频繁被 Killed / 502 | 内存 OOM。`dmesg -T \| grep -i "killed process"` 确认；`free -h` 看 available。1.7G 机器上 `-Xmx` 不得超过 512m |

## 13. 安全基线（已内置，开场前不需要额外操作）

> 本节记录的是**代码/配置里已经做好的**防护，不是待办清单。

### 13.1 认证与密钥

| 项 | 状态 | 说明 |
|---|---|---|
| JWT 签名密钥 | 必须环境变量注入 | `application.yml` 无默认值，`TokenService` 启动时校验「≥32 字节 + 非若依开源默认值」，不达标**拒绝启动**。实测弱密钥与空密钥均被拒绝 |
| 管理端鉴权 | 接口级 `@PreAuthorize` | 与菜单可见性**无关**，隐藏菜单后直接调接口仍会被 403 |
| 登录限流 | 验证码 + 密码错误 5 次锁 10 分钟 | RuoYi 原生能力 |

### 13.2 抽奖大屏免登录的边界

大屏投屏与运行同机，操作员直接按空格抽奖，**刻意不加登录**（现场便利优先）。
免登录不等于无防护，靠三条**不增加任何操作步骤**的约束兜住业务完整性：

| 防护 | 实现 | 实测 |
|---|---|---|
| 按 IP 限流 | `@RateLimiter(time=10, count=20, limitType=IP)` | 连发第 21 次即被拦，返回「访问过于频繁」 |
| 操作审计 | `@Log` 记录每次抽奖/作废/切场次 | 已写入 `sys_oper_log`，含来源 IP |
| 阻断跨站调用 | `ResourcesConfig` 默认不开放任何 CORS 来源 | 带 `Origin: https://evil.example.com` 的请求无放行头；同源不受影响 |

> `LogAspect` 已做匿名容错（`SecurityUtils.getLoginUser()` 对免登录接口会抛异常，
> 原本会让审计整条丢失）。现匿名接口记 IP + URL + 入参，满足追溯。

若后续要收紧为需登录：去掉 `DrawScreenController` 类上的 `@Anonymous`，改用权限点即可。

| 项 | 状态 |
|---|---|
| MySQL 端口 | 绑定 `127.0.0.1`，同网段无法直连 |
| 后端 8080 / Redis 6379 | 未映射到宿主机，仅容器网络内可达 |
| `ry` 测试账号 | 已从基线 `sql/00-ry-base.sql` 删除（不再创建） |
| 普通角色授权 | 已收回全部原生菜单，只保留 KCon 菜单。**仅隐藏菜单不收回授权是无效防护** |
| SQL 注入 | kcon 全部 Mapper 一律 `#{}` 参数化，无 `${}` 拼接 |

### 13.4 已知未处理项

| 项 | 说明 |
|---|---|
| HTTP 明文传输 | 已在公网运行但**仍是明文 HTTP**，签到会提交手机号，属**已知未完成项**。必须尽快上 HTTPS（见 15.1）。当前实例 `123.57.9.62` |

3. **隐私合规**：名单含真实姓名/手机号/公司/邮箱，公网可达后需隐私政策与会后销毁承诺。

### 15.2 应补

4. **接口限流复核**：现有按 IP 限流（见 13.4 脚注），公网暴露后应评估是否需加人机校验，防止脚本遍历手机号探测名单。
5. **服务器运维监控**：内存仅 1.7G 无 swap，需监控 available 与 OOM；磁盘 5.1G 镜像 + 2.8G 构建缓存待清理。

### 15.3 改动范围（上 HTTPS 时）
| 层 | 现状（HTTP） | 上 HTTPS 后 |
|---|---|---|
| 镜像 | `kcon-backend` / `kcon-web` | **不变** |
| 编排 | `docker-compose.yml` | 复用，仅覆盖 `.env` |
| 入口 | 80 端口 + 公网 IP | **加一层 HTTPS**（Caddy 自动签发，或 Nginx + certbot） |
| 地址 | `http://123.57.9.62/kconluck2026/sign/` | `https://kcon.xxx.com/kconluck2026/sign/` |
| 二维码 | 指向公网 IP | 指向域名 |

### 15.4 验收项
| 编号 | 验收项 | 通过标准 |
|---|---|---|
| AC-16 | HTTPS | 全站强制 HTTPS，证书自动续期 |
| AC-17 | 防刷 | 同一 IP/设备高频请求被限流，遍历探测无响应 |
| AC-18 | 域名可达 | 二维码指向域名而非 IP，扫码即到签到页 |

## 17. 对外交付镜像使用说明

拿到镜像的人按本节操作，不需要改代码、不需要额外配 CORS。

### 17.1 镜像与架构

| 镜像 | 说明 |
|---|---|
| `ghcr.io/hxhy00/kconlucky-backend` | Spring Boot 后端（含 MySQL/Redis 驱动） |
| `ghcr.io/hxhy00/kconlucky-web` | 三端静态站 + nginx 统一入口 |

- tag：`latest`（仅 main）、`sha-<短SHA>`（可精确回滚）
- **单 manifest 双架构**：`linux/amd64` + `linux/arm64`，x86 服务器 / Apple Silicon / ARM 云主机直接 `docker pull` 即可，无需 `--platform`
- 需要锁定架构时：`docker pull --platform linux/arm64 <镜像>`

### 17.2 CORS：不需要配置

- 三端页面与接口**同源**：nginx 把 `/{前缀}/prod-api/` 反代到 `backend:8080`，浏览器不产生跨域请求
- 后端默认不开放跨域（`cors.allowed-origins` 为空 = 不返回 CORS 头），这是刻意的
- 只有把前端单独部署到**其他域名/端口**时才需要开放：
  ```yaml
  environment:
    CORS_ALLOWED_ORIGINS: https://admin.example.com,https://screen.example.com
  ```

### 17.3 部署前缀（默认 `/kconluck2026/`）

- 预构建镜像固定挂在 `/kconluck2026/` 下：`/admin/`（管理端）、`/sign/`（签到）、`/screen/`（大屏）、`/prod-api/`（接口）
- 从源码换前缀只改构建参数，不必改源码：
  ```bash
  docker build -f docker/web/Dockerfile --build-arg DEPLOY_PREFIX=myapp -t kcon/web:myapp .
  ```
  三端静态资源基址、nginx location 会一并与 `/myapp/` 对齐
- `.env` 的 `KCON_BASE_PATH` 只影响运维脚本（preflight/start）的探测路径，改前缀时同步修改

### 17.4 运行前提

| 项 | 要求 |
|---|---|
| 必需环境变量 | `MYSQL_ROOT_PASSWORD`、`TOKEN_SECRET`（缺失时 compose 直接拒绝启动） |
| 端口 | `WEB_PORT`（默认 80）；`MYSQL_DEBUG_PORT` 仅绑定 127.0.0.1 |
| 数据卷 | `data/mysql`、`data/redis`、`data/web-static`、`data/upload`、`data/backup`、`logs/` |
| 首次启动 | 空卷时自动灌入 `sql/` 基线（三脚本）；已有数据不会覆盖 |
| 健康检查 | 四个容器均带 healthcheck，`docker compose ps` 应显示 healthy |
| 日志 | backend 日志落 `logs/backend/`（`LOG_PATH=/app/logs`），容器重建不丢 |

配置模板见仓库根目录 `.env.example`：`cp .env.example .env` 后按注释填写即可。
