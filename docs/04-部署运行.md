# KCon 2026 签到 + 抽奖系统 · 部署运行

**版本**：v3.3（Docker Compose + 离线内网）
**日期**：2026-10-13
**部署方案**：**方案 B · Docker Compose 一键编排**（已确认）
**目标环境**：**内网/离线单机**（Mac）运行，会场一台笔记本；系统**不联互联网**，投屏与运行同一台笔记本
**分期**：**第一期**本地跑通并支撑现场；**第二期**迁至公网服务器 + 域名（见第 15 节）

---

## 1. 方案总览

一句话：**一套镜像 + 一份编排**，全程离线运行。

```
【会前 · 联网电脑】                      【现场 · 笔记本 · 完全离线】
 改代码 → docker compose build            拷入镜像包 + 项目目录
      → docker save 导出镜像 tar   ────►  docker load 导入镜像
      → 打包项目目录（含 .env/sql）        docker compose up -d
                                              ↓
                    观众手机（连笔记本热点/会场WiFi）→ 扫码 http://<IP>/sign 自助签到
                    签到台水牌二维码 → 观众截图 → 工作人员发胸牌
                    笔记本 HDMI → 投屏大屏（抽奖）
```

选方案 B 的理由：
1. 现场不怕环境问题——机器上只要有 Docker，JDK / Node / MySQL 版本全部锁死在镜像里，**不需要现场联网装依赖**。
2. 换机迁移不靠记忆——镜像用 `docker save/load` 搬，数据在宿主机目录，拷走即可。
3. 开发机与现场机行为一致，避免「我这儿能跑」。
4. 现场完全离线，符合「不上互联网」要求，安全且不受会场网络质量影响。

> **关键概念：会前构建，现场只启动。** 现场不做任何 `build`、不 `npm install`、不拉镜像。

## 2. 架构

```
                     ┌──────────────────────────────────────────┐
   观众手机  ──────► │  nginx-web 容器（前端总入口 :80）          │
   （自助扫码）      │   /            → 入口分流页（选入口）      │
                     │   /admin/      → 管理端（静态）            │
                     │   /screen/     → 抽奖大屏（静态）          │
                     │   /sign/       → 签到 H5（静态）           │
                     │   /prod-api/   → 反向代理到 backend:8080   │
                     └───────────────┬──────────────────────────┘
                                     │ 容器内网络
                                     ▼
                     ┌──────────────────────────┐      ┌────────────────────────┐
   笔记本 HDMI ────► │  backend 容器（:8080）    │─────►│  mysql 容器（:3306）    │
   投大屏            │  RuoYi-Vue 后端 jar       │ JDBC │  volume → ./data/mysql │
                     └──────────────────────────┘      └────────────────────────┘
                                                                       │
                                                          ./data/mysql 持久化目录
```

**关键点**
- 只有 `nginx-web` 对外暴露 80 端口，**观众用自己的手机**扫码，需能访问 `http://<笔记本IP>/sign`。
- 根路径 `/` 是**入口分流页**（列出管理端 / 大屏 / 签到三个入口），不是签到页；签到页固定在 `/sign/`，避免误把签到页当管理端打开。
- 三端前端共用同一个后端域名与端口，**不存在跨域问题**（同源 `/prod-api/` 反代）。
- MySQL 不对外暴露端口（`3307:3306` 仅为本机调试用，可关闭），避免现场误连。
- 笔记本的 3306 已被现有 `mysql` 容器占用，本系统 MySQL 映射到 **3307**，互不干扰。

## 4. 配置（`.env`，唯一需要现场改的文件）

```dotenv
# ---- 对外端口 ----
WEB_PORT=80                 # 三端统一入口；80 冲突时改 8081 等
MYSQL_DEBUG_PORT=3307       # 仅本机调试用，已强制绑定 127.0.0.1

# ---- 数据库 ----
MYSQL_ROOT_PASSWORD=root123
MYSQL_DATABASE=kcon_lucky

# ---- 后端 ----
BACKEND_PORT=8080
TZ=Asia/Shanghai

# ---- 令牌密钥（必填）----
# JWT 签名密钥。必须 ≥32 字节随机串，不能用若依开源默认值。
# 生成方式：openssl rand -base64 48
# 后端启动时会校验，不达标直接拒绝启动（避免配漏了却在现场裸奔）
TOKEN_SECRET=<用 openssl rand -base64 48 生成>

# ---- 现场信息（用于生成签到二维码与展示地址）----
LAN_IP=192.168.1.100        # 内网部署填本机局域网 IP；公网部署填域名或公网 IP
```

> **`TOKEN_SECRET` 是必填项**：`.env` 里没有它，`docker compose up` 会直接报错并提示，
> 这是刻意设计——不留「忘配就用弱默认值」的口子。

### 4.0 内网部署 vs 公网部署

`LAN_IP` 的填法取决于部署形态，二者的网络前提完全不同：

| 部署形态 | `LAN_IP` 填什么 | 观众手机的前提 |
|---|---|---|
| 第一期·内网单机 | 运行笔记本的局域网 IP，如 `192.168.1.100` | 与笔记本同一 WiFi / 同一网段 |
| 第二期·公网服务器 | 对外域名或公网 IP，如 `kcon.example.com` | **只要能上网即可**，无需同一网络 |

管理端数据总览的提示文案已按两种形态通用化，不写死「同一局域网」。

> 公网部署还必须补 HTTPS（见第 15 节）：签到页要提交手机号，明文 HTTP 不可接受。
> 二维码指向的地址也会自动变成 `https://kcon.example.com/sign/`。

### 4.1 管理端部署基路径（三处必须一致）

管理端挂在 `/admin/` 子路径下，以下三处都写 `/admin/`：

| 位置 | 配置项 | 值 |
|---|---|---|
| `ruoyi-ui/.env.production` / `.env.staging` | `VUE_APP_BASE_PATH` | `/admin/` |
| `ruoyi-ui/.env.development` | `VUE_APP_BASE_PATH` | `/` |
| `ruoyi-ui/vue.config.js` | `publicPath` | 取 `VUE_APP_BASE_PATH`，不另行硬编码 |
| `docker/web/nginx.conf` | `location /admin/` | `/admin/` |

`VUE_APP_BASE_PATH` 是**唯一来源**，有三个用途：vue-router 的 `base`（决定路由 path 与实际 URL 的对应关系）、
`vue.config.js` 的 `publicPath`（静态资源前缀）、以及 `location.href` 硬跳转的路径前缀。
缺 base 会导致刷新或直接访问子页面时路径错位。

> 值**必须以 `/` 结尾**。`vue.config.js` 已加构建期断言，配错会在 `npm run build` 阶段直接报错，
> 不会带着错误配置构建出包。

## 5. `docker-compose.yml`

```yaml
services:
  mysql:
    image: mysql:8.0
    container_name: kcon-mysql
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD}
      MYSQL_DATABASE: ${MYSQL_DATABASE}
      TZ: ${TZ}
    command:
      - --character-set-server=utf8mb4
      - --collation-server=utf8mb4_general_ci
    volumes:
      - ./data/mysql:/var/lib/mysql
      # 首次初始化按文件名顺序执行，四个脚本缺一不可：
      # 少了 kcon_migrate_v2.sql 会缺 kcon_winner.email 等对象，抽奖直接报 Unknown column
      - ./sql/00-ry-base.sql:/docker-entrypoint-initdb.d/00-ry-base.sql:ro
      - ./sql/kcon_lucky.sql:/docker-entrypoint-initdb.d/01-kcon_lucky.sql:ro
      - ./sql/kcon_menu.sql:/docker-entrypoint-initdb.d/02-kcon-menu.sql:ro
      - ./sql/kcon_migrate_v2.sql:/docker-entrypoint-initdb.d/03-kcon-migrate_v2.sql:ro
    ports:
      - "${MYSQL_DEBUG_PORT:-3307}:3306"    # 仅调试，可不暴露
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "127.0.0.1", "-p${MYSQL_ROOT_PASSWORD}"]
      interval: 5s
      timeout: 3s
      retries: 20
    networks: [kcon]

  backend:
    build:
      context: ./ruoyi
      dockerfile: ../docker/backend/Dockerfile
    image: kcon-backend:1.0
    container_name: kcon-backend
    restart: unless-stopped
    environment:
      SPRING_PROFILES_ACTIVE: druid
      SPRING_DATASOURCE_DRUID_MASTER_URL: jdbc:mysql://mysql:3306/${MYSQL_DATABASE}?useUnicode=true&characterEncoding=utf8&zeroDateTimeBehavior=convertToNull&useSSL=false&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true
      SPRING_DATASOURCE_DRUID_MASTER_USERNAME: root
      SPRING_DATASOURCE_DRUID_MASTER_PASSWORD: ${MYSQL_ROOT_PASSWORD}
      TZ: ${TZ}
    depends_on:
      mysql:
        condition: service_healthy
    networks: [kcon]

  web:
    build:
      context: .
      dockerfile: docker/web/Dockerfile
      args:
        LAN_IP: ${LAN_IP}
    image: kcon-web:1.0
    container_name: kcon-web
    restart: unless-stopped
    ports:
      - "${WEB_PORT}:80"
    depends_on: [backend]
    networks: [kcon]

networks:
  kcon:
    driver: bridge
```

> **配置外置**：后端不打包任何数据库地址，全部通过 `SPRING_DATASOURCE_*` 环境变量注入，
> 满足「配置集中、不硬编码」要求（见 01-需求规格 11.4）。

## 6. Dockerfile

### 6.1 `docker/backend/Dockerfile`（多阶段构建）

```dockerfile
# --- 构建阶段 ---
FROM maven:3.9-eclipse-temurin-17 AS build
WORKDIR /src
# 先拷 pom，利用 Docker 层缓存加速依赖下载（国内源见 settings.xml）
COPY pom.xml ./
COPY ruoyi-admin/pom.xml ruoyi-admin/
COPY ruoyi-common/pom.xml ruoyi-common/
COPY ruoyi-framework/pom.xml ruoyi-framework/
COPY ruoyi-system/pom.xml ruoyi-system/
COPY ruoyi-quartz/pom.xml ruoyi-quartz/
COPY ruoyi-generator/pom.xml ruoyi-generator/
COPY docker/maven-settings.xml /root/.m2/settings.xml
RUN mvn -B dependency:go-offline -DskipTests
COPY . .
RUN mvn -B clean package -DskipTests

# --- 运行阶段 ---
FROM eclipse-temurin:17-jre
WORKDIR /app
ENV TZ=Asia/Shanghai JAVA_OPTS="-Xms256m -Xmx768m"
COPY --from=build /src/ruoyi-admin/target/ruoyi-admin.jar app.jar
EXPOSE 8080
ENTRYPOINT ["sh", "-c", "java $JAVA_OPTS -jar app.jar"]
```

`docker/maven-settings.xml` 用阿里云镜像（国内源）：

```xml
<mirror>
  <id>aliyun</id>
  <mirrorOf>*</mirrorOf>
  <url>https://maven.aliyun.com/repository/public</url>
</mirror>
```

### 6.2 `docker/web/Dockerfile`（三端统一构建 + Nginx）

```dockerfile
# --- 三端依次构建 ---
FROM node:20-alpine AS build
ARG LAN_IP=127.0.0.1
WORKDIR /src
COPY ruoyi-ui/package*.json ruoyi-ui/
RUN cd ruoyi-ui && npm config set registry https://registry.npmmirror.com && npm ci
COPY ruoyi-ui/ ruoyi-ui/
RUN cd ruoyi-ui && npm run build:prod

COPY checkin-h5/package*.json checkin-h5/
RUN cd checkin-h5 && npm config set registry https://registry.npmmirror.com && npm ci
COPY checkin-h5/ checkin-h5/
RUN cd checkin-h5 && npm run build

COPY screen/package*.json screen/
RUN cd screen && npm config set registry https://registry.npmmirror.com && npm ci
COPY screen/ screen/
RUN cd screen && npm run build

# --- 运行阶段 ---
FROM nginx:1.27-alpine
COPY docker/web/nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /src/ruoyi-ui/dist     /usr/share/nginx/html/admin
COPY --from=build /src/checkin-h5/dist   /usr/share/nginx/html/checkin
COPY --from=build /src/screen/dist       /usr/share/nginx/html/screen
EXPOSE 80
```

### 6.3 `docker/web/nginx.conf`

```nginx
server {
    listen 80;
    server_name _;
    client_max_body_size 20m;          # 名单 Excel 上传

    # 根路径：入口分流页（管理端 / 大屏 / 签到）
    location = / { root /usr/share/nginx/html; try_files /index.html =404; }
    location = /index.html { root /usr/share/nginx/html; }   # index/try_files 会内部跳转到此，必须单列

    # 签到 H5：观众入口。必须 = /sign + ^~ /sign/ 两段式，
    # 单一 location /sign 是前缀匹配，会把 /signup、/signin 也吞进来
    location = /sign { return 301 /sign/; }
    location ^~ /sign/ { alias /usr/share/nginx/html/checkin/; index index.html; try_files $uri $uri/ /sign/index.html; }

    # 管理端 / 抽奖大屏：无尾斜杠入口统一 301
    location = /admin  { return 301 /admin/; }
    location = /screen { return 301 /screen/; }
    location /admin/  { alias /usr/share/nginx/html/admin/;  index index.html; try_files $uri $uri/ /admin/index.html; }
    location /screen/ { alias /usr/share/nginx/html/screen/; index index.html; try_files $uri $uri/ /screen/index.html; }

    # 兜底：nginx 镜像内没有 /etc/nginx/html，落到默认 location 会变成 nginx 硬 404 页
    location / { return 404; }

    # 后端反向代理（同源，天然无跨域）
    location /prod-api/ {
        proxy_pass http://backend:8080/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_read_timeout 60s;
    }
}
```

> 三端前端的构建 `base` 需分别配为 `/admin/`、`/screen/`、`/sign/`，接口基址统一为 `/prod-api`。
> 实际生效的配置以 `docker/web/nginx.conf` 为准，本节只作说明用。

## 7. 日常使用

> **会前开发机（联网）** 才执行 `--build`；**现场笔记本（离线）** 只用 `up -d` 启动已导入的镜像。

```bash
cd /Users/hxhy/Code/KconLucky

# 【会前】改动代码后：重新构建并启动（需联网）
docker compose up -d --build

# 【现场】启动已导入的镜像（离线，不 build）
docker compose up -d

# 查看状态与日志
docker compose ps
docker compose logs -f backend

# 停止（保留数据）
docker compose down

# 重启单个服务
docker compose restart backend
```

**访问地址**（假设 `LAN_IP=192.168.1.100`、`WEB_PORT=80`）：

| 端 | 地址 | 说明 |
|---|---|---|
| 入口分流页 | `http://192.168.1.100/` | 三个入口的导航页，认不准 URL 时开这个 |
| 管理端 | `http://192.168.1.100/admin/` | 登录入口 |
| 管理端落地页 | `http://192.168.1.100/admin/index` | 登录后自动进入（渲染数据总览） |
| 抽奖大屏 | `http://192.168.1.100/screen/` | 投屏用，按 F11 全屏 |
| 观众签到 | `http://192.168.1.100/sign/` | **二维码指向此地址**，观众扫码即到 |
| 后端 API（调试） | `http://192.168.1.100/prod-api/` | 一般无需手动访问 |

**抽奖大屏快捷键**（仅操作员在投屏机上使用，**不显示在投屏画面上**）：

| 按键 | 作用 |
|---|---|
| `空格` | 抽奖（滚动 → 定格） |
| `Backspace` | 作废当前中奖，号码回池，可重抽 |
| `1` | 切到上午场 |
| `2` | 切到下午场 |

> 早期版本把这行说明写在画面底部，全场观众都能看到「按退格作废」这类内部信息，已移除。

**抽奖控制台 → 大屏设置**：可在页面上直接维护大屏底部的「支持单位」文案（多个用逗号分隔，中英文逗号都认），保存后大屏约 3 秒自动生效，无需改代码发版。留空则不显示赞助商条。配置落库在 `sys_config` 的 `kcon.sponsors`，容器重启不丢。

**管理端登录后的九个页面**（多人共用同一 `admin` 账号，按现场时序排列）：

| 页面 | 地址 | 什么时候用 |
|---|---|---|
| 数据总览 | `/admin/dashboard` | 登录后默认页；签到率统计 + 签到二维码下载 |
| 参会名单 | `/admin/attendee` | 开场前导入名单 |
| 抽奖控制台 | `/admin/draw` | 管理端抽奖、切场次、看剩余可抽号数 |
| 兑奖核验 | `/admin/verify` | 活动中高频；凭端口号 + 手机号核验发放 |
| 中奖日志 | `/admin/log/winner` | 结束后复盘 |
| 核验日志 | `/admin/log/verifylog` | 事后追溯「谁核验发放的」 |
| 奖品设置 | `/admin/setting/prize` | 开场前配置奖项档位 |
| 数据管理 | `/admin/setting/data` | 一页两 tab：数据清场（开场前一次性）+ 数据迁移（备份/恢复，限超管） |

> **菜单结构**：4 个一级平铺页（数据总览 / 参会名单 / 抽奖控制台 / 兑奖核验）+
> 2 个目录（「日志」「设置」），目录下的子菜单 URL 为 `/{目录}/{子菜单}`（如 `/log/winner`）。
> 一级页面的路由就是菜单 `path` 本身（如 `/admin/dashboard`），**不带 `/kcon` 前缀**。

> **关于 `/admin/index`**：登录落地页用的是**静态路由**（与若依原生首页 `/index` 同机制）。
> 动态路由要等登录后拉取菜单才注册，静态重定向若指向动态路由（`/dashboard`），
> 会在路由注册前解析，落进 404。因此落地页固定为 `/admin/index`，`meta.activeMenu`
> 让侧边栏「数据总览」保持高亮，两条路径渲染的是同一个看板组件。

> 管理台已隐藏 RuoYi 原生的「首页 / 系统管理 / 系统监控 / 系统工具 / 若依官网」等现场用不到的菜单。
> 多人共用同一账号时，操作互不踢下线；但**清场**与**奖品设置**建议由固定一人操作，避免误改。

> **投屏与运行同机**：大屏直接在这台笔记本上按 F11 全屏打开 `/screen/`，不需要额外放行其他 IP。

**默认账号**：`admin / admin123`（首次登录后立即改密码）。

## 8. 会前打包 → 现场离线运行（核心流程）

现场**没有互联网**，所以镜像必须在会前的联网电脑上构建好，以 tar 包形式带过去。

### 8.1 会前（联网电脑）

```bash
cd KconLucky
docker compose build                                    # 构建四个镜像
docker save kcon-backend:1.0 kcon-web:1.0 \
            mysql:8.0 redis:7-alpine  > kcon_images.tar
tar czf kcon_offline_pkg.tar.gz \
    docker-compose.yml .env docker/ sql/ kcon_images.tar
```

把 `kcon_offline_pkg.tar.gz` 拷到现场笔记本（U 盘即可）。

### 8.2 现场（离线笔记本）

**前置**：笔记本已安装 Docker Desktop（这一步会前装好，需联网下载安装包）。

```bash
tar xzf kcon_offline_pkg.tar.gz -C ~/KconLucky && cd ~/KconLucky
docker load < kcon_images.tar        # 导入镜像，无需联网
# 按现场实际修改 .env 里的 LAN_IP（必要时改 WEB_PORT）
docker compose up -d                 # 只启动，不 build
docker compose ps                    # 应看到四个容器 Up / healthy
```

### 8.3 现场网络要求（**第一期最大风险点**）

观众是**用自己手机扫码**签到的，所以观众手机必须能访问到笔记本。这一节是第一期能否成功的决定性条件。

| 项 | 要求 |
|---|---|
| 外网 | **不需要**，全程离线即可运行 |
| 局域网 | 观众手机需能访问 `http://<LAN_IP>:<WEB_PORT>/sign/`。两条路径：① 接入**会场 WiFi**（需与笔记本同网段）；② 笔记本开**热点**（带机量有限，见下） |
| 访客隔离 | 会场 WiFi 若开启「AP 隔离」（也叫客户端隔离），手机会连不上笔记本，**必须在 T-1 演练时实测** |
| DNS | 不需要，全部用 IP 访问 |
| **承载能力** | 普通笔记本热点带机量约 8–20 台；商用 AP 单台约 50–100。300–1000 人**不同时在线**（签完即走）时通常可用，但**必须实测** |
| 兜底 | 若会场 WiFi 不可用且热点不够，**启用备用方案**：在签到台放 2–3 台平板，工作人员代输手机号（此时需要的是平板能上网，压力大幅降低） |

> **备选降级路径**：若实测发现网络撑不住，可**临时切换为「工作人员代操作」模式**——签到页本身不区分操作者，平板打开同一个页面即可，代码无需改动。这是本方案刻意保留的弹性。

### 8.4 现场部署清单（T-1 演练 + 当天）

| 步骤 | 操作 | 通过标准 |
|---|---|---|
| 1 | 会前完成 `docker compose build` 与 `docker save` | 镜像 tar 生成成功 |

## 10. 换电脑迁移（方案 B 的收益点）

### 10.1 迁移 = 拷目录

### 10.2 迁移注意

| 事项 | 说明 |
|---|---|
| 架构一致 | 镜像与 CPU 架构绑定：旧机 Apple Silicon、新机 x86 时，镜像需用 `docker save` 的对应架构版本，或在**联网**新机上重建 |

## 12. 故障排查

| 现象 | 排查 |
|---|---|
| `web` 起不来，80 被占 | `lsof -i:80`；改 `.env` 的 `WEB_PORT` |
| `backend` 反复重启 | `docker compose logs backend`；多为 MySQL 未就绪，看 healthcheck 是否通过 |
| 登录后先跳 404，点返回才进管理端 | 静态 `redirect` 指向了动态路由。动态路由要等 `GenerateRoutes` 才注册，`redirect` 在 `beforeEach` 之前解析必然落进 404。`router/index.js` 里 `/` 的 `redirect` 只能是静态路由（本项目为 `'index'`） |
| 刷新页面后样式丢失或跳分流页 | 管理端 vue-router 没配 `base`。`ruoyi-ui/.env.production` 的 `VUE_APP_BASE_PATH` 须为 `/admin/`，与 `vue.config.js` 的 `publicPath`、`nginx` 的 `location /admin/` 三处一致 |
| 退出登录后跳到根路径分流页 | `location.href` 硬跳转未带 base。`request.js`、`Navbar.vue` 里应拼 `process.env.VUE_APP_BASE_PATH`，不能写死 `/index` |
| 打开 `http://<IP>/` 却是签到页 | 镜像版本旧（v3.2 及以前根路径就是签到页）。执行 `docker compose up -d --build web` 重建；新版本根路径为分流页，签到页在 `/sign` |
| 管理端菜单出现「系统管理/系统监控/若依官网」 | `sql/kcon_menu.sql` 未重新导入。用 `scripts/` 下的菜单初始化方式重跑，或执行该文件中的 `UPDATE sys_menu SET visible='1' WHERE menu_id IN ('1','2','3','4','5')` |
| 观众扫码打不开 | 手机与笔记本不在同一 WiFi / 开了访客隔离；`ping <LAN_IP>` 验证连通性；人多了连不上 → 启用 8.3 的平板代操作降级路径 |
| 二维码指向 `127.0.0.1` | `.env` 的 `LAN_IP` 未填或未生效（手机扫到的是手机自己的 127.0.0.1）。改 `.env` 后 `docker compose up -d backend` 重建容器 |
| 签到页空白、控制台报资源 404 | 签到 H5 的 `base` 与 nginx 路径不一致。`checkin-h5/vite.config.js` 须为 `base: '/sign/'`，nginx 须有 `location ^~ /sign/`；资源实际从 `/sign/assets/*` 取，**不需要**为 `/assets/` 单独配规则 |
| 打开 `/admin` 或 `/screen`（漏尾斜杠）是 nginx 错误页 | 镜像内没有 `/etc/nginx/html`，落到默认 location 就是 nginx 硬 404。已配 `location = /admin { return 301 /admin/; }`，若出现说明 nginx 配置被改动过 |
| `/signup`、`/signin` 之类的路径返回了签到页 | `location /sign` 是前缀匹配，会吞掉所有同前缀路径。必须用 `location = /sign` + `location ^~ /sign/` 两段式 |
| 构建报「VUE_APP_BASE_PATH 必须以 / 结尾」 | `.env.production` / `.env.staging` 里的 `VUE_APP_BASE_PATH` 少了尾部斜杠。这是构建期断言，属于预期行为 |
| 后端起不来，日志报 `token.secret 未配置或强度不足` | `.env` 缺 `TOKEN_SECRET`，或值不足 32 字节 / 用了若依开源默认值。执行 `openssl rand -base64 48` 生成后写入 `.env`。这是刻意的拒绝启动，不是 bug |
| `docker compose up` 报 `必须在 .env 中配置 TOKEN_SECRET` | 同上，compose 层的必填校验先于容器启动拦下了 |
| 大屏抽奖返回「访问过于频繁」 | 触发了 `@RateLimiter(10秒20次)`。正常现场操作（数秒一次）不会触发；若确实需要更高上限，调大 `DrawScreenController` 上的 `count` |
| 管理端菜单里出现了系统管理等原生菜单 | 只执行了菜单 SQL 的 INSERT 部分。需确认 `kcon_menu.sql` 完整执行（含隐藏原生菜单 + 收回普通角色授权） |
| 用 `ry` 账号登录提示账号停用 | 预期行为。`ry` 是 RuoYi 自带测试账号，现场只用 `admin`，已在 SQL 中停用 |
| 签到页能开但接口 502 | `backend` 未起或 nginx 反代路径不对（检查 `/prod-api/` 末尾斜杠） |
| 端口号重复 | 查 `kcon_port_pool` 是否存在重复 `port_no`（应为 PK，不可能重复）；确认未被手工改库 |
| `docker compose up` 报拉不到镜像 | 现场离线环境下误触发了 build/pull；应先 `docker load < kcon_images.tar`，再 `up -d`（不带 `--build`） |
| 构建时依赖拉不动 | 构建只应在**会前联网电脑**执行；已配阿里云 / npmmirror 国内源 |
| `docker load` 后镜像架构不符 | 会前打包时确认笔记本 CPU 架构（Apple Silicon 用 `--platform linux/arm64` 构建） |

## 13. 安全基线（已内置，开场前不需要额外操作）

> 本节记录的是**代码/配置里已经做好的**防护，不是待办清单。

### 13.1 认证与密钥

| 项 | 状态 | 说明 |
|---|---|---|
| JWT 签名密钥 | 必须环境变量注入 | `application.yml` 无默认值，`TokenService` 启动时校验「≥32 字节 + 非若依开源默认值」，不达标**拒绝启动**。实测弱密钥与空密钥均被拒绝 |
| 管理端鉴权 | 接口级 `@PreAuthorize` | 与菜单可见性**无关**，隐藏菜单后直接调接口仍会被 403 |
| 登录限流 | 验证码 + 密码错误 5 次锁 10 分钟 | RuoYi 原生能力 |

### 13.2 抽奖大屏免登录的边界

大屏投屏与运行同机，操作员直接按空格抽奖，**刻意不加登录**（现场便利优先）。
免登录不等于无防护，靠三条**不增加任何操作步骤**的约束兜住业务完整性：

| 防护 | 实现 | 实测 |
|---|---|---|
| 按 IP 限流 | `@RateLimiter(time=10, count=20, limitType=IP)` | 连发第 21 次即被拦，返回「访问过于频繁」 |
| 操作审计 | `@Log` 记录每次抽奖/作废/切场次 | 已写入 `sys_oper_log`，含来源 IP |
| 阻断跨站调用 | `ResourcesConfig` 默认不开放任何 CORS 来源 | 带 `Origin: https://evil.example.com` 的请求无放行头；同源不受影响 |

> `LogAspect` 已做匿名容错（`SecurityUtils.getLoginUser()` 对免登录接口会抛异常，
> 原本会让审计整条丢失）。现匿名接口记 IP + URL + 入参，满足追溯。

若后续要收紧为需登录：去掉 `DrawScreenController` 类上的 `@Anonymous`，改用权限点即可。

### 13.3 数据库与中间件

| 项 | 状态 |
|---|---|
| MySQL 端口 | 绑定 `127.0.0.1`，同网段无法直连 |
| 后端 8080 / Redis 6379 | 未映射到宿主机，仅容器网络内可达 |
| `ry` 测试账号 | 已在 `sql/kcon_menu.sql` 中停用（`status='1'`） |
| 普通角色授权 | 已收回全部原生菜单，只保留 KCon 菜单。**仅隐藏菜单不收回授权是无效防护** |
| SQL 注入 | kcon 全部 Mapper 一律 `#{}` 参数化，无 `${}` 拼接 |

### 13.4 已知未处理项

| 项 | 说明 |
|---|---|
| HTTP 明文传输 | 第一期内网可接受；第二期公网**必须**上 HTTPS（15.3 节列为强制项） |
| 签到接口无频次限制 | `/app/checkin/query` 未加限流。第二期公网部署前需补 `@RateLimiter`，防手机号批量枚举 |

## 15. 第二期：公网服务器 + 域名（另立一期）

### 15.1 为什么单独一期
第一期目标是**现场跑通**，现场有网络不确定性。公网版解决该问题，但引入备案、HTTPS、防护、隐私合规等新工作量，**不混在第一期做**，避免两边都做不扎实。

### 15.2 改动范围（预估很小）
| 层 | 第一期（本地） | 第二期（公网） |
|---|---|---|
| 镜像 | `kcon-backend` / `kcon-web` | **不变** |
| 编排 | `docker-compose.yml` | 复用，仅覆盖 `.env` |
| 入口 | 80 端口 + IP 或热点 | **加一层 HTTPS**（建议用 **Caddy** 自动签发，或 Nginx + certbot） |
| 地址 | `http://<LAN_IP>/sign/` | `https://kcon.xxx.com/sign/` |
| 二维码 | 指向内网 IP | 指向域名 |

### 15.3 公网版必须补齐
1. **HTTPS** 强制：签到页要提交手机号，明文 HTTP 不可接受。
2. **域名与 ICP 备案**：国内服务器需等备案通过（约 1–3 周），**需尽早启动**。
3. **接口限流与人机校验**：防止有人用脚本批量遍历手机号探测名单。
4. **隐私合规**：名单含真实姓名/手机号/公司/邮箱，需隐私政策与会后销毁承诺。
5. **抽奖与兑奖留在现场内网**：公网只承载签到；抽奖大屏与兑奖核验建议仍在本地，避免被外部影响。
6. **现场兜底**：公网不可用时，能切回本地实例继续签到（第一期的本地部署保留为备份）。

### 15.4 验收项（第二期）
| 编号 | 验收项 | 通过标准 |
|---|---|---|
| AC-15 | 公网签到 | 观众在任何网络下扫码签到成功，无需连会场 WiFi |
| AC-16 | HTTPS | 全站强制 HTTPS，证书自动续期 |
| AC-17 | 防刷 | 同一 IP/设备高频请求被限流，遍历探测无响应 |
| AC-18 | 数据一致 | 公网签到数据与现场内网一致（或明确单一数据源） |
