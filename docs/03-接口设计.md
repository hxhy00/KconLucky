# KCon 2026 签到 + 抽奖系统 · 接口设计

**版本**：v2.0
**日期**：2026-10-12
**协议**：HTTP / JSON（RESTful 风格）
**基础路径**：`/admin`（管理端业务接口）+ `/app`（免登录端：签到、大屏）；RuoYi 自带 `/system`、`/login`（管理端鉴权）

---

## 1. 约定

- 统一响应体（沿用 RuoYi `AjaxResult`）：
```json
{ "code": 200, "msg": "操作成功", "data": { } }
```
- 公开接口（签到端、大屏端）**无需登录**，走独立前缀；v0.4.0 起因现场共用出口 IP，已取消按 IP 限流。
- 管理端接口需 RuoYi 登录 Token（`Authorization: Bearer xxx`）。
- 手机号返回一律掩码：`138****0001`。

| 前缀 | 用途 | 鉴权 |
|---|---|---|
| `/app/checkin/**` | 签到端 H5 | 无 |
| `/app/screen/**` | 抽奖大屏端 | 无（可加简单口令） |
| `/admin/**` | 管理端 | RuoYi Token |

> **导出类接口统一用 POST**：前端 `this.download()`（RuoYi 全局混入）内部是 `service.post`，
> 所有 `/export`、`/template`、`/signsheet` 都必须是 `@PostMapping`，
> 写成 `@GetMapping` 会返回 `Request method 'POST' is not supported`。

## 2. 签到端接口

### 2.1 查询参会人
`POST /app/checkin/query`

**请求**
```json
{ "keyword": "13800138000" }
```
| 字段 | 说明 |
|---|---|
| keyword | 完整 11 位手机号；格式不符返回非 200 + 提示「请输入完整 11 位手机号」 |

**响应（命中）**
```json
{
  "code": 200,
  "data": {
    "matchType": "single",
    "signed": false,
    "attendee": {
      "id": 12,
      "name": "张三",
      "phoneMask": "138****8000",
      "company": "某某安全",
      "position": "安全研究员"
    }
  }
}
```

> `position` = 职务/职位，为空时不展示该行。（`attendCount` 字段已随「第几次参加 KCon」废弃而移除）
> 手机号全场唯一，`matchType` 固定为 `single`；签到端不再支持后四位或候选卡片。
> **`query` 不返回 `ticketType` / `channel`**：查询阶段不暴露权益类型与渠道来源。`submit` / `lookup` 会返回 `ticketType`（权益类型）供成功页/找回页展示；所有接口都不返回 `drawEligible`。

**响应（0 人）**
```json
{ "code": 500, "msg": "查无此人，请联系现场工作人员" }
```
> 代码层由 `ServiceException` 统一返回非 200；前端只按 `code !== 200` 展示 `msg`。

### 2.2 确认签到
`POST /app/checkin/submit`

**请求**
```json
{ "attendeeId": 12, "phone": "13800138000" }
```
| 字段 | 说明 |
|---|---|
| attendeeId | 查询接口返回的参会人 ID |
| phone | 完整 11 位手机号；服务端与名单等值比对后才落库 |

> **公网版加固**：submit 免登录且会真实落库，只传自增 `attendeeId` 就等于允许批量替人签到、
> 耗尽端口池。因此 `phone` 为必填且必须是完整 11 位；不匹配返回「手机号与参会人信息不匹配，请重新查询」。
> 查询阶段同样只接受完整 11 位，后四位已全部下线。

**响应（首次签到 / 重复签到统一返回原端口号）**
```json
{
  "code": 200,
  "data": {
    "signed": true,
    "portNo": 38217,
    "checkinTime": "2026-11-01 09:12:33",
    "repeat": false,
    "name": "张三",
    "ticketType": "含自助午餐、伴手礼",
    "tip": "您的抽奖端口号为 38217，请您截屏保存，用于兑换抽奖礼品；请向工作人员出示此截图领取胸牌"
  }
}
```
> `repeat=true` 表示重复签到，端口号不变。
> `ticketType` 即「权益类型」，仅用于签到成功页展示；没有权益时为空。
> **spec 006**：非买票者照常签到、照常领端口号，仅不进抽奖池；但本接口**不返回**任何抽奖资格字段
> （FR-A5：签到端免登录，回传资格等于开放口径自查）。买票者与赠票/嘉宾拿到的报文完全一致。
> 抽奖资格的判定只存在于服务端的抽奖池计算中（`specs/006-draw-only-paid-ticket/spec.md` 2.2）。

### 2.3 按手机号回查（找回端口号）
`POST /app/checkin/lookup`，请求体 `{"keyword": "13800138000"}`

**只接受完整 11 位手机号**，返回该手机号的签到状态与端口号（未签到则 `signed=false`）。

> **为什么是 POST 而非 GET**：nginx access_log 的 `$request` 会记录完整请求行，
> GET 查询串会把观众手机号明文写进访问日志（还会留在浏览器历史里），POST body 则不会。
> 限流已于 v0.4.0 移除（现场观众共用出口 IP，按 IP 分桶会误伤签到）。
>
> **为什么不再支持后四位**：本接口免登录，而尾号空间仅 10^4，枚举一遍成本极低，
> 等于把「谁在场、尾号是多少、端口号是多少」全量敞开。更关键的是兑奖核验的防冒领
> 判定正是「本人知道完整手机号」（见 §4.5 核验接口），找回端可枚举会让这层判定失去意义。
> 砍掉尾号分支后，枚举面从 10^4 收敛到 10^11。

| 入参 | 说明 |
|---|---|
| `keyword` | 完整 11 位手机号；不匹配时返回 `signed=false` + `msg` 提示 |

**响应（已签到）**
```json
{
  "code": 200,
  "data": {
    "signed": true,
    "portNo": 38217,
    "checkinTime": "2026-11-01 09:12:33",
    "name": "张三",
    "ticketType": "含自助午餐、伴手礼"
  }
}
```
> `ticketType` 即「权益类型」，用于找回结果展示；没有权益时为空。
> **spec 006**：找回接口同样**不返回**抽奖资格字段——否则免登录的找回端会变成
> 「输入手机号即知自己在不在池里」的自查接口（FR-A5）。

签到端主流程与找回入口现在**统一只接受完整 11 位手机号**；后四位查询与候选卡片已下线。

## 3. 抽奖大屏端接口

> **大屏只读**。抽奖、作废、切场次等一切写操作均已收归管理端「抽奖控制台」（见 §4），
> 大屏只保留 `/status` 一个读接口，靠轮询被动感知新批次与场次变化。
> 免登录的 `/app/screen` 下不再存在任何写端点——避免大屏成为绕过权限控制的后门。

### 3.1 获取当前场次与统计
`GET /app/screen/status`

带上上次收到的 `version` 时走增量：后端发现无变化只回 `{ "unchanged": true, "version": "..." }`，
大屏据此跳过整份重渲染（投屏中重渲染会打断中奖动画）。

```json
{
  "code": 200,
  "data": {
    "sessionCode": "AM",
    "sessionName": "上午场",
    "checkedInToday": 512,
    "poolCount": 498,
    "winnerCount": 3,
    "currentTier": { "id": 1, "tierName": "三等奖", "quantity": 3, "drawnCount": 1 }
  }
}
```

> 此处仅列出大屏实际消费的字段。响应还含 `sessions`（场次列表）与 `tiers`（各档位进度）：
> 前者供管理端复用，后者用于大屏进度条可视化。
>
> **本接口免登录，因此响应体不含 `excludedCount`**（spec 006 FR-A8）。该字段会让
> `checkedInToday − poolCount` 的差额含义被任意匿名请求读到，等于公布筛选口径。
> 后端 `screenStatus()` 为管理端与大屏共用，敏感字段一律由管理端控制器自行附加——
> 保护的对象是**报文**，不是界面。详见 `specs/006-draw-only-paid-ticket/spec.md` §4.6。

> 全部需登录，对应 4.3 节的页面功能。

### 4.1 名单管理（Excel 导入 + CRUD）
| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/admin/attendee/import` | 上传 Excel/CSV（`mode=append\|replace`） |
| GET | `/admin/attendee/list` | 分页列表（支持姓名/手机/公司/渠道/职务·年级/签到状态/是否参与抽奖筛选） |
| GET | `/admin/attendee/{id}` | 查看单条详情 |
| POST | `/admin/attendee` | **新增**单条（手机号唯一校验） |
| PUT | `/admin/attendee` | **修改**单条 |
| DELETE | `/admin/attendee/{ids}` | **删除**（已签到人员默认禁止删除） |
| POST | `/admin/attendee/template` | 下载导入模板 |
| POST | `/admin/attendee/signsheet` | 下载**统一签到表**（姓名/手机号/渠道标识/票种/打钩列，按姓名排序，供签到台打印） |

**新增/修改请求体**
```json
{
  "id": 12,
  "name": "张三",
  "phone": "13800138000",
  "channel": "嘶吼平台卖票",
  "ticketType": "含自助午餐、帽衫、伴手礼",
  "drawEligible": 1,
  "company": "某某安全",
  "email": "zhangsan@example.com",
  "position": "安全研究员"
}
```
| 字段 | 必填 | 校验 |
|---|---|---|
| name | 是 | 长度 ≤ 64 |
| phone | 是 | 唯一；11 位手机号格式 |
| channel | 是 | 渠道来源，必须命中渠道来源映射白名单；旧数据可为 `S/T/C/H/D/G/V` 单字母，不做枚举校验 |
| ticketType | 是 | 权益类型，自由文本，长度 ≤ 128；如 `含自助午餐、伴手礼`、`无`，不做枚举校验 |
| drawEligible | 否 | `1`=参与 `0`=不参与（spec 006）；缺省按 0 入库（与导入口径一致：只有显式「是」才进池） |
| company | 否 | 长度 ≤ 128 |
| email | 否 | 邮箱格式 |
| position | 否 | 自由文本，长度 ≤ 64，不校验格式 |

（`attendCount` 字段已随「第几次参加 KCon」废弃而移除）

| GET | `/admin/benefit/list` | 权益发放日志分页查询：`portNo`、`name`、`params[beginTime/endTime]` 筛选；**类型由服务端固定为 BENEFIT**，请求参数无法改写 | `kcon:benefit:list` |

**手机号重复响应**
```json

```
**删除已签到响应**

### 4.4.1 抽奖控制台
| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| GET | `/admin/draw/status` | 抽奖池实时状态（**只读，控制台每 5 秒轮询**） | `kcon:draw:query` |
| POST | `/admin/draw/draw` | 抽一档（一次抽出该档剩余全部）；响应顺带回 `status` | `kcon:draw:operate` |
| POST | `/admin/draw/void-batch` | 撤回当前场次最近抽出的整档，号码回池 | `kcon:winner:void` |
| POST | `/admin/draw/session` | 切换当前抽奖场次 | `kcon:draw:operate` |

> 作废走 `kcon:winner:void`（与抽奖操作 `kcon:draw:operate` 刻意分离）：
> 抽奖台操作员若同时能作废，就能把自己抽出的记录撤回重抽。
> 单条作废走兑奖侧的 `POST /admin/verify/void/{winnerId}`（中奖日志页按钮），
> 控制台的 `/admin/draw/void` 因前端从未调用已删除。

`/admin/draw/status` 响应体：

```json
{
  "code": 200,
  "data": {
    "sessionCode": "AM",
    "sessionName": "上午场",
    "checkedInToday": 512,
    "poolCount": 498,
    "excludedCount": 14,
    "winnerCount": 3,
    "sessions": [{ "code": "AM", "name": "上午场" }, { "code": "PM", "name": "下午场" }],
    "currentTier": { "id": 1, "tierName": "三等奖", "quantity": 3, "drawnCount": 1 },
    "tiers": [{ "id": 1, "tierName": "三等奖", "quantity": 3, "drawnCount": 1 }],
    "lastWinner": { "id": 33, "portNo": 38217, "name": "张三", "tierName": "三等奖", "winTime": "2026-11-01 10:20:31" },
    "winnerGroups": [
      {
        "sessionCode": "AM",
        "sessionName": "上午场",
        "tiers": [
          {
            "tierId": 1,
            "tierName": "三等奖",
            "quantity": 3,
            "drawnCount": 3,
            "winners": [
              { "winnerId": 31, "portNo": 38217, "name": "张三", "company": "某某安全",
                "statusText": "已中奖", "winTime": "2026-11-01 10:20:31" }
            ]
          }
        ]
      }
    ]
  }
}
```

| 字段 | 说明 |
|---|---|
| `tiers` | **只含当前场次**的档位进度，供「当前应抽档位」判定与撤回操作使用 |
| `lastWinner` | 当前场次最近一条仍可作废的中奖记录（`status=0`），撤回按钮的启用依据与档位提示 |
| `winnerGroups` | **每个场次的全部档位**（含未抽过的档位，`winners` 为空数组），档位按 `draw_order` 升序（三等 → 二等 → 一等）。控制台「奖项进度与中奖记录」横栏表格的数据源：同一行同时给出该档的 `quantity`/`drawnCount` 与中奖人，回答「没抽的有多少 / 抽了多少 / 抽中的是谁」。只统计 `status != 2`，`statusText` 为 `已中奖`/`已领取` |

> `winnerGroups` 单独存在的理由：`tiers` 只有当前场次，切到另一场时拿不到该场档位配置，
> 未抽过的档位会从表里消失；因此后端按场次返回**完整档位骨架**，前端不再推算总量。

### 4.5 兑奖核验（双因子）
`POST /admin/verify`，body：
```json
{ "portNo": 6531, "phone": "13800000003" }
```

| 参数 | 说明 |
|---|---|
| portNo | 端口号（必填） |
| phone | 完整 11 位手机号（必填，不接受后四位） |

**响应**（`data.result` 四态）：
```json
{
  "code": 200,
  "data": {
    "result": "VALID",          // VALID=通过 / NOT_ISSUED=无中奖记录 / PHONE_MISMATCH=手机号不符 / RECEIVED=已领取过
    "msg": "核验通过",
    "winnerId": 1,
    "name": "王五",
    "company": null,
    "position": null,
    "tierName": "三等奖",
    "sessionCode": "AM"
  }
}
```

> **响应刻意不含任何手机号掩码**（既无 `phoneMask` 也无 `holderMask`）。
> 核验台是公开工位：掩码（`138****0003`）配上端口号，就是一条「本人可自助核验」的旁路——
> 围观者即使看到尾号，也无法通过签到端查询/找回（两端都只接受完整 11 位手机号），必须知道完整号码才能通过核验。
> 身份应由「本人当场报出完整 11 位手机号」证明，而非由系统回显。掩码仅在后台日志与导出中留痕。

**确认发放**：`POST /admin/verify/receive`，body 同上。后端先复核（非 VALID 直接拒绝），通过后置 `status=1`；权限 `kcon:verify:receive`。

> **发放不可逆**：`updateStatus` 对 `status=1` 的更新强制带 `and status = 0` 条件，
> 只能从「未领取」单向流转到「已领取」；并发重复发放时受影响行数为 0 并抛错，
> 由数据库条件更新兜底，不依赖应用层锁。

> **发放成功写一条奖品发放日志** `kcon_benefit_grant`（type=PRIZE，输入手机号脱敏存储），
> 在「日志 → 奖品发放」独立查询/导出，与权益发放日志互不共用页面。
> **核验动作本身不再留痕**：原核验日志 `kcon_verify_log` 已退役（表与历史数据保留）。

### 4.6 系统迁移（备份 / 恢复）
| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| POST | `/admin/migrate/export` | 导出全量数据（生成 .sql 下载）。**必须是 POST**：前端走统一下载方法（POST + blob + Authorization 请求头），早期写成 `@GetMapping` 会与之不匹配，且 Token 放隐藏域会 401 | `hasRole('admin')` |
| POST | `/admin/migrate/restore` | 导入 .sql 恢复数据（multipart，字段 `file` + `password`）。恢复前自动存档当前数据，存档失败即中止；整体覆盖，不可逆。**2026-10-21 起加密码校验**：`password` 为当前登录人本人密码，校验不通过时连上传的临时文件都不落盘 | `hasRole('admin')` + 本人密码 |

> 权限口径：**`hasRole('admin')` + 本人密码**，没有 `kcon:data:migrate` 权限点。
> `sql/kcon_menu.sql` 刻意不创建该权限点，避免留下一个谁也不校验的空壳权限。
>
> 2026-10-21 起新增的第二层是**密码**（见 4.7 的双重校验表），不是权限点：
> 恢复会整体覆盖数据库，破坏力比清场更大，因此同样要求输入当前登录人本人的密码。
>
> 实现细节：`restore` 的 `file` 参数必须声明 `required = false`。若写成 `@RequestParam("file")`，
> 缺文件时 Spring 会在进入方法**之前**抛 `MissingServletRequestPartException`，
> 密码校验根本没机会执行 —— 表现为「密码错了却提示请选择文件」，让密码校验形同虚设。

### 4.7 数据导出与清场
| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| POST | `/admin/data/export` | 签到全量明细 Excel 流（含姓名/手机号/渠道/票种/端口号/签到时间/**权益发放状态**/是否中奖/奖项/领取状态；不含「第几次参加 KCon」——已废弃）。同 4.6，走 POST + blob 下载 | `kcon:attendee:export` |
| GET | `/admin/data/qrcode.png` | 签到页二维码 PNG（后端 ZXing 本地生成，离线可用） | `kcon:attendee:list` |
| POST | `/admin/data/reset` | 清场：名单/签到/中奖/核验日志/发放日志清空，端口池归零，已抽数归零；不可恢复。**请求体必带 `{"password": "<当前登录人密码>"}`** | `kcon:data:reset` + 本人密码 |

#### 清场的双重校验（2026-10-21 起）

| 层 | 校验 | 挡住什么 |
|---|---|---|
| 1 | `@PreAuthorize("@ss.hasPermi('kcon:data:reset')")` | 没权限的人。该权限只授予超管角色，`kcon_staff`（现场工作人员）不持有，猜到接口地址也是 403 |
| 2 | `SensitiveOperationGuard#verifyCurrentUserPassword` | 「电脑没锁屏被别人顺手点一下」；同时让每次清场都能在操作日志里对应到具体执行人 |

第 2 层用 BCrypt 比对**当前登录人自己的密码**，不是硬编码常量、也不是独立专用密码：

- 工作人员拿自己的密码调不通（第一层就 403）；
- 知道别人密码但没登录成对方账号也没用；
- 密码连续输错 5 次锁定 30 分钟（按 `userId` 计数，进程内内存态，重启即清零）。

错误文案：`请输入数据清场所需的管理员密码` / `管理员密码不正确，还可尝试 N 次` /
`密码错误次数过多，请 N 分钟后再试`。

> 恢复接口同样走第 2 层校验，理由相同且更充分 —— 恢复会整体覆盖数据库。

## 5. 参会名单字段（导入/导出模板）

**标准模板 6 列**，按表头名识别、顺序不限。必填 3 列（姓名 / 手机号 / 渠道来源），其余选填；
**权益类型与「是否参与抽奖」不在模板里**——它们完全由渠道来源映射决定，避免导入与映射两套事实源打架。

| # | 表头 | 必填 | 说明 |
|---|---|---|---|
| 1 | 姓名 | 是 | 长度 ≤ 64 |
| 2 | 手机号 | 是 | 业务主键，全场唯一；必须为 11 位手机号 |
| 3 | 渠道来源 | 是 | 必须命中「设置 → 渠道来源」中的已配置渠道 |
| 4 | 公司 | 否 | 可缺省，管理端补录 |
| 5 | 职位 | 否 | 职场人填职务（`CTO`），学生填年级（`大二`） |
| 6 | 邮箱 | 否 | 可缺省，管理端补录 |

> **渠道来源是硬白名单**：未配置映射的渠道整行计为 blocker，正式导入**整批拒绝**（预检返回 `BLOCK` 并列出问题行）；
> 不再有「回退行内值」或「跳过几行、放行其余」的行为。空映射表 = 一个渠道都不放行（手工新增同理）。
> **旧 9 列表头不再支持**（`渠道标识` / `票种` / `是否参与抽奖` 等），导入会直接提示使用 6 列模板。
> **映射增删改会重算存量名单**：改权益类型会同步到未手工改过的人；人工改过权益的（`ticket_type_manual=1`）保持原值。
> 金额、购票时间、发票需求等其余票务字段不属于本系统，由票务总表管理。

**导入模板下载**（`/admin/attendee/template`）生成的文件正好 6 列；名单导出含「权益发放 / 权益发放时间」列（2026-10-23 起，「第几次参加 KCon」列已废弃移除）。

## 7. 前后端联调注意

0. **接口基址**：三端生产环境统一走**同源反代** `/prod-api/`（Nginx 转发到 `backend:8080`，见《04-部署运行》），因此**无跨域问题**；仅本地开发时用各自 devServer 的 proxy 指向 `http://localhost:8080`。
1. 签到端 H5 与大屏端为**独立前端工程**，开发期若不配 proxy，则由后端 CORS 放行（仅本机网段）。
2. 大屏端轮询 `/app/screen/status`（建议 2–5 秒）刷新统计。
3. 所有时间字段格式：`yyyy-MM-dd HH:mm:ss`。
