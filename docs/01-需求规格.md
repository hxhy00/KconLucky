## 1. 背景与目标

### 1.1 业务背景
- KCon 2026 与「人工智能+」大会同场举办。
- 票务源：嘶吼（主力）、TGO、崔牛会、活动行、对公票、赠票、VIP/嘉宾/媒体票。
- 票务侧已有独立的《票务总表》与渠道对照表管理票种、金额、购票时间等；本系统消费「参会名单」，**名单含「渠道标识」**用于现场签到分流，其余票务字段不重复承载。

### 1.2 系统目标
1. **现场自助签到**：参会人自己手机扫码 → 输手机号/后四位 → 确认身份 → 签到，端口号显示在**手机屏幕**上。
2. **签到即分配唯一随机端口号（1–65535）**，作为抽奖与兑奖的唯一凭证。
3. **管理端**：名单管理、签到实时监控、分场次抽奖操作、兑奖核验、数据统计导出。
4. **抽奖大屏端**：深色炫酷大屏，滚动抽号，分上午/下午场，一号只中一次，可作废重抽。
5. **第一期单机本地部署**（数据不出本机），公网版作为**第二期**独立推进（见第 12 节）。

### 1.3 系统形态
| 端 | 使用者 | 技术形态 | 屏幕 |
|---|---|---|---|
| 签到端 H5 | 参会观众 | 手机浏览器打开的轻量网页（Tailwind 可） | 手机 |
| 管理端 | 签到台工作人员 / 市场组 / 兑奖工作人员 | RuoYi-Vue 自带后台（Element UI） | 笔记本 |
| 抽奖大屏端 | 主持人 / 抽奖操作员 | 独立轻量大屏页面（Tailwind + 动效库） | 投屏大屏 |

> 三端共用一套 SpringBoot 后端 API（RuoYi-Vue）。

## 2. 名词解释（对齐术语）

| 名词 | 含义 |
|---|---|
| **端口号** | 签到成功时系统随机分配的 1–65535 整数，全场唯一、不放回。抽奖与兑奖的唯一凭证。 |
| **场次** | 抽奖场次，分 `上午场`、`下午场`。 |
| **抽奖池** | 某场次可参与抽奖的人集合。**在点击抽奖按钮的瞬间锁定**。 |
| **已中奖** | 该端口号已抽中某奖项，自动移出抽奖池，不可再中。 |
| **已领取** | 中奖人到兑奖台核验通过并领走奖品。 |
| **作废重抽** | 中奖人不在场，作废该条记录，号码**回池**可再次被抽中。 |
| **参会名单** | 票务侧汇总后交付给本系统的名单。**导入只需 4 列**：姓名 / 手机号 / **渠道标识** / 票种；**公司 / 邮箱 / 第几次参加 KCon / 职务·年级** 4 个字段为选填，缺失不阻塞，可在管理端补录。 |
| **渠道标识** | 名单第 3 列，单字母票源编码（`S`嘶吼 / `T`TGO / `C`崔牛会 / `H`活动行 / `D`对公 / `G`赠票 / `V`嘉宾VIP媒体），取值见《票源渠道对照表》；系统原样存储展示，不做枚举校验。 |
| **票种** | 名单第 4 列，如 `散客票` / `早鸟票` / `标准票` / `合作渠道票` / `对公票` / `赠票` / `嘉宾票`。现场按票种分流与统计用，原样存储、自由文本、不做枚举校验。 |
| **第几次参加 KCon** | 该观众累计参加 KCon 的届数（整数，如 `3` 表示第 3 次参加）。选填，缺失留空。 |
| **职务/年级** | 单列存储。职场人填职务（如 `CTO`、`安全研究员`），学生填年级（如 `大二`、`研一`）。选填，系统原样展示，不做拆分与校验。 |
| **胸牌** | 会前批量印刷的通用证件，**人人一致，不印端口号**（端口号签到时才随机产生，无法预印）。 |
| **端口号凭证** | 端口号唯一存在于**签到成功页（观众手机屏幕）**，观众自行截图保存；截图仅用于签到环节领取胸牌（出示截图 → 工作人员在签到表打钩 → 发胸牌），兑奖环节以系统核验为准。 |
| **统一签到表** | 管理端导出的纸质签到表（含渠道列），签到台工作人员用于发放胸牌时打钩核对。 |

## 3. 用户与场景

| 角色 | 使用端 | 场景 |
|---|---|---|
| 参会观众 | 签到 H5（自己手机） | 扫签到台二维码 → 输手机号（或后四位）→ 确认身份 → 签到 → 手机屏幕显示端口号 → **截图** |
| 签到台工作人员 | 管理端 + 肉眼看截图 | 看观众手机截图确认已签到 → **在统一签到表上打钩** → 发放胸牌；处理查不到名单的观众 |
| 市场组 | 管理端 | 上传/追加/替换参会名单、导出签到数据 |
| 主持人/抽奖操作员 | 抽奖大屏端 | 选择场次 → 点抽奖 → 宣布中奖 → 作废重抽（如需） |
| 兑奖工作人员 | 管理端（兑奖核验页） | 报端口号+手机号+姓名 → **系统核验（不看截图）** → 点「已领取」 |

## 5. 关键流程

### 5.1 签到流程（观众自助）
```
观众到前台，扫签到台水牌二维码（自己手机）
        ↓
输入手机号 / 后四位
   ├─ 命中 1 人 → 展示身份 → 点「确认签到」
   ├─ 命中多人 → 候选卡片列表 → 点「是我」 → 点「确认签到」
   └─ 命中 0 人 → 提示联系工作人员（走人工/嘉宾通道）
        ↓
分配随机端口号（不放回）→ 手机成功页大字展示 + 截图提示
        ↓
观众截图 → 出示给前台工作人员 → 工作人员目视确认 → 在统一签到表上打钩 → 发放胸牌
```

> **风险说明**：本环节以截图作为已签到的凭据，截图可伪造/转发。因胸牌为通用物料、价值低，接受此风险；**兑奖环节不适用此做法**，见 5.3。

### 5.2 抽奖流程
```
主持人打开大屏 → 选场次（上午/下午）
        ↓
   点「抽下一档」→ 后台锁定此刻抽奖池 → 把当前档位剩余名额一次抽完
        ↓
   大屏逐个揭晓：第 1 / N 位 → 端口号滚动 → 定格 + 显示姓名 + 公司
        ↓
   全部揭晓完停在汇总页（本档全部中奖者 + 端口号）
        ↓
   ├─ 人都在场 → 点「抽下一档」继续抽下一个等级
   └─ 有人不在场 → 点该位的「撤回」→ 名额退回本档，再点「抽下一档」补抽缺的那位
```

> 抽奖粒度：**一次点击 = 抽完一档**（不是一个人）。滚动特效是「一个人一个人的端口号滚动」，
> 属于揭晓动画，不代表一次只抽一个人。

### 5.3 兑奖核验流程（双因子 · 不认截图）
```
领奖人到兑奖台，口头报【端口号 + 完整 11 位手机号】
        ↓
管理端核验页输入 端口号 + 手机号
        ↓
   系统校验：
   ├─ 端口号未发放 → 拦截：「该端口号未发放，可能为伪造截图」
   ├─ 端口号有效但手机号不匹配 → 拦截：「手机号与持号人不符」
   └─ 两者匹配 → 显示 姓名/手机掩码/公司/邮箱/奖项/状态
        ↓
   工作人员目视核对姓名，一致 → 点「已领取」→ 发奖
        ↓
   写入核验日志（谁在什么时候核验/发放了哪个号）
```

> 领奖人即便出示截图，工作人员也**必须以系统核验结果为准**，截图仅作参考。

| 数据安全 | 数据仅存本机 MySQL，不上传任何外部服务器 |
| 隐私 | 管理台与核验结果中手机号一律掩码显示（`138****0001`） |
| 可用性 | 签到端极简，三步完成；输错号有明确引导 |
| 可恢复 | 数据实时落库，断电重启不丢 |
| **可迁移** | 整套系统可**迁移到另一台电脑**运行：数据可整体导入导出，配置集中在单文件，不依赖本机特定路径 |

## 9. 约束与依赖

1. 运行环境：全栈 Docker Compose（含 JDK 17 + SpringBoot、MySQL 8.0、Node.js 构建 + Nginx），宿主机只需 Docker。
2. 名单质量依赖：必须提供**姓名 + 手机号 + 渠道标识 + 票种**四列，缺手机号无法自助签到；**公司、邮箱、「第几次参加 KCon」、「职务/年级」可为空**，不阻塞签到，可在管理端补录。
3. **网络依赖（第一期）**：观众用自己手机扫码签到，因此观众手机必须能访问到笔记本地址（同一 WiFi 网段且无 AP 隔离，或笔记本开热点）。**这是第一期的最大风险点**，需会前实测承载量。
4. 奖品：**档位与数量**入库并由后台配置；**具体实物方案不录入**，现场按实际情况发放。
5. **离线运行**：现场无外网。镜像与依赖在会前于另一台联网电脑完成构建，现场只做 `docker compose up -d`。

## 11. 系统可迁移（换电脑部署）

### 11.1 目标
整套系统（程序 + 数据 + 配置）能从一台电脑**完整迁移**到另一台电脑，新机器上不丢数据、不改代码即可运行。

### 11.2 迁移需要搬的三样东西
| 类别 | 内容 | 迁移方式 |
|---|---|---|
| **数据** | `./data/mysql`（MySQL 数据目录） | 随项目目录一起打包拷贝 |
| **程序** | 四个 Docker 镜像（可由新机重建） | 拷镜像 tar 包，或在新机 `docker compose build` |
| **配置** | `.env`（端口、密码、`LAN_IP`） | 一个文件，只改 IP/端口 |

### 11.3 迁移方式：**Docker Compose 一键迁移（已确认）**

采用 **方案 B · Docker Compose**，详细实施见《04-部署运行》。

1. 一份 `docker-compose.yml` 定义 **四个容器**：MySQL、后端、Web（统一入口，托管管理端 + 签到 H5 + 抽奖大屏三套静态资源并反代 API）。
2. 数据落在**宿主机目录** `./data/mysql`（不是匿名卷，便于直接拷走）。
3. 配置集中在 `.env`（端口、密码、`LAN_IP`），后端数据库连接全部由环境变量注入，不硬编码。
4. 迁移 = 打包项目目录（含 `data/`）→ 新机解压 → `docker compose up -d`。
5. 现场只暴露一个端口（默认 80），三端同源，无跨域。
6. 同一份镜像与编排**可原样搬到公网服务器**（第二期只需换 `.env` + 加 HTTPS 层），无需改代码。

### 11.4 设计要求（无论哪种方案都要满足）
1. **配置外置**：数据库地址/账号/密码集中在 `application-druid.yml`，不硬编码在代码里。
2. **无本机绝对路径依赖**：所有资源路径用相对路径或配置项。
3. **数据一键备份/恢复**：管理端提供「导出全量数据」按钮（生成 .sql 下载），新机可导入。
4. **端口号池可重建**：`kcon_port_pool` 由脚本生成，新机导入即恢复。
5. **幂等初始化**：首次启动自动建表/初始化场次与奖品档位（或提供一键初始化脚本）。

### 11.5 验收
| 编号 | 验收项 | 通过标准 |
|---|---|---|
| AC-11 | 数据导出 | 管理端能导出全量数据 .sql 文件 |
| AC-12 | 跨机迁移 | 全新电脑装好 Docker，解压项目 + `docker compose up -d` 即完整跑起来，数据一致 |
| AC-13 | 断网可用 | 会前已完成镜像构建，现场无外网仍能签到与抽奖 |
| AC-14 | 可重复启动 | `docker compose down` 后再 `up`，数据与端口号不变 |

## 12. 公网版（第二期 · 另立一期）

### 12.1 定位
第一期先在本机跑通并支撑现场。第二期把同一套系统搬到**公网服务器 + 域名**，让观众**无需连现场 WiFi**即可扫码签到，彻底消除第一期的最大风险点。

### 12.2 与第一期的关系
- **同一套代码与镜像**，改动仅限：`.env` 配置、域名与 HTTPS、部署位置。
- 不得为公网版单独分叉一套代码（避免两套逻辑漂移）。

### 12.3 必须补齐的能力（本期不做，但设计需预留）
| # | 能力 | 说明 |
|---|---|---|
| 1 | **HTTPS** | 必须。表单提交手机号，明文 HTTP 不可接受 |
| 2 | **域名与备案** | 国内服务器需 ICP 备案，会前提前走流程 |
| 3 | **公网防护** | 限流、防刷、人机校验（防止批量遍历手机号探测名单） |
| 4 | **隐私与合规** | 名单含真实姓名/手机号/公司/邮箱，需隐私政策、最小化收集、会后数据销毁承诺 |
| 5 | **数据落点** | 明确数据存于哪台服务器、谁可访问、留存多久 |
| 6 | **抽奖与签到解耦** | 公网只承载**签到**；抽奖大屏与兑奖核验仍建议在**现场内网**跑，避免外界干扰 |
| 7 | **断电与断网兜底** | 公网断开时，现场应能切到本地实例继续签到 |

### 12.4 待决策（第二期启动时确认）

2. 抽奖环节是否也上公网，还是坚持现场内网？
3. 公网实例与现场实例的数据如何同步（现场为主 / 公网为主）？
