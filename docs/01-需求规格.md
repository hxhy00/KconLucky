## 1. 背景与目标

### 1.1 业务背景
- KCon 2026 与「人工智能+」大会同场举办。
- 票务源：嘶吼（主力）、TGO、崔牛会、活动行、对公票、赠票、VIP/嘉宾/媒体票。
- 票务侧已有独立的《票务总表》与渠道对照表管理票种、金额、购票时间等；本系统消费「参会名单」，**名单含「渠道标识」**用于现场签到分流，其余票务字段不重复承载。

### 1.2 系统目标
1. **现场自助签到**：参会人自己手机扫码 → 输入完整 11 位手机号 → 确认身份 → 签到，端口号显示在**手机屏幕**上。
2. **签到即分配唯一随机端口号（1–65535）**，作为抽奖与兑奖的唯一凭证。
3. **管理端**：名单管理、签到实时监控、分场次抽奖操作、兑奖核验、数据统计导出。
4. **抽奖大屏端**：深色炫酷大屏，滚动抽号，分上午/下午场，一号只中一次，可作废重抽。
5. **第一期单机本地部署**（数据不出本机），公网版作为**第二期**独立推进（见第 12 节）。

### 1.3 系统形态
| 端 | 使用者 | 技术形态 | 屏幕 |
|---|---|---|---|
| 签到端 H5 | 参会观众 | 手机浏览器打开的轻量网页（Tailwind 可） | 手机 |
| 管理端 | 签到台工作人员 / 市场组 / 兑奖工作人员 | RuoYi-Vue 自带后台（Element UI） | 笔记本 |
| 抽奖大屏端 | 主持人 / 抽奖操作员 | 独立轻量大屏页面（Tailwind + 动效库） | 投屏大屏 |

> 三端共用一套 SpringBoot 后端 API（RuoYi-Vue）。

## 2. 名词解释（对齐术语）

| 名词 | 含义 |
|---|---|
| **端口号** | 签到成功时系统随机分配的 1–65535 整数，全场唯一、不放回。抽奖与兑奖的唯一凭证。 |
| **场次** | 抽奖场次，分 `上午场`、`下午场`。 |
| **抽奖池** | 某场次可参与抽奖的人集合。**在点击抽奖按钮的瞬间锁定**。 |
| **已中奖** | 该端口号已抽中某奖项，自动移出抽奖池，不可再中。 |
| **已领取** | 中奖人到兑奖台核验通过并领走奖品。 |
| **作废重抽** | 中奖人不在场，作废该条记录，号码**回池**可再次被抽中。 |
| **参会名单** | 票务侧汇总后交付给本系统的名单。**导入只需 6 列**：姓名 / 手机号 / 渠道来源（必填）+ 公司 / 职位 / 邮箱（选填）；权益类型与参与抽奖由渠道来源映射带出，缺失不阻塞，可在管理端补录。 |
| **渠道标识** | 名单第 3 列，单字母票源编码（`S`嘶吼 / `T`TGO / `C`崔牛会 / `H`活动行 / `D`对公 / `G`赠票 / `V`嘉宾VIP媒体），取值见《票源渠道对照表》；系统原样存储展示，不做枚举校验。 |
| **票种** | 名单第 4 列，如 `散客票` / `早鸟票` / `标准票` / `合作渠道票` / `对公票` / `赠票` / `嘉宾票`。现场按票种分流与统计用，原样存储、自由文本、不做枚举校验。（历史字段，「第几次参加 KCon」已于 2026-10-23 废弃删除） |
| **权益发放** | 工作人员在参会名单页对已签到观众点「发放」登记权益领取。一人一条、发放后不可撤销；重复领取由系统硬拦截（DB 唯一键）。记录见「日志 → 权益发放」，与奖品发放是两个页面。 |
| **职务/年级** | 单列存储。职场人填职务（如 `CTO`、`安全研究员`），学生填年级（如 `大二`、`研一`）。选填，系统原样展示，不做拆分与校验。 |
| **胸牌** | 会前批量印刷的通用证件，**人人一致，不印端口号**（端口号签到时才随机产生，无法预印）。 |
| **端口号凭证** | 端口号唯一存在于**签到成功页（观众手机屏幕）**，观众自行截图保存；截图仅用于签到环节领取胸牌（出示截图 → 工作人员在签到表打钩 → 发胸牌），兑奖环节以系统核验为准。 |
| **统一签到表** | 管理端导出的纸质签到表（含渠道列），签到台工作人员用于发放胸牌时打钩核对。 |

## 3. 用户与场景

| 角色 | 使用端 | 场景 |
|---|---|---|
| 参会观众 | 签到 H5（自己手机） | 扫签到台二维码 → 输入完整 11 位手机号 → 确认身份 → 签到 → 手机屏幕显示端口号 → **截图** |
| 签到台工作人员 | 管理端 + 肉眼看截图 | 看观众手机截图确认已签到 → **在统一签到表上打钩** → 发放胸牌；处理查不到名单的观众 |
| 市场组 | 管理端 | 上传/追加/替换参会名单、导出签到数据 |
| 主持人/抽奖操作员 | 管理端（抽奖控制台）+ 投屏大屏 | 在控制台选场次 → 点抽奖 → 大屏只读展示与揭晓 → 宣布中奖 → 如需在控制台作废重抽 |
| 兑奖工作人员 | 管理端（兑奖核验页） | 报端口号+手机号+姓名 → **系统核验（不看截图）** → 点「已领取」 |

### 3.1 系统角色与权限分工

现场用一套管理端，但**操作权限按角色分离**，避免工作人员误触破坏性功能（2026-10-21 起）：

| 角色 | `role_key` | 能用什么 | 明确不能用 |
|---|---|---|---|
| 超级管理员 | `admin` | 全部功能，含数据清场 / 全量备份迁移 / 奖品设置 / 渠道映射 / 中奖作废 | — |
| 签到台 | `kcon_checkin_staff` | 数据总览、参会名单（查/增/改/导出/**权益发放**）、日志（权益发放 / 中奖 / 奖品发放，均只查） | 删名单、名单导入、抽奖、兑奖发放、作废中奖、发放日志导出、全部设置类 |
| 抽奖台 | `kcon_draw_staff` | 数据总览、参会名单（只读）、抽奖控制台（抽奖/切场次）、日志（权益发放 / 中奖 / 奖品发放，均只查） | 名单增删改、权益发放、兑奖发放、**作废中奖**（作废只留给超管，杜绝自己抽自己撤）、发放日志导出、全部设置类 |
| 兑奖台 | `kcon_verify_staff` | 数据总览、参会名单（只读）、兑奖核验（含**确认发放**）、日志（权益发放 / 中奖 / 奖品发放；奖品发放可导出） | 名单增删改、权益发放（与奖品发放分离）、抽奖、作废中奖、权益发放日志导出、全部设置类 |
| 参会观众 | 无账号 | 签到 H5 | 管理端一切功能 |

**一人多岗**：RuoYi 支持一账号绑定多个角色，建号时岗位可多选（如「签到台 + 兑奖台」），
换班叠加绑定即可，无需建新号。

**为什么岗位角色不复用 `common`**：`common` 原本持有「删名单」「作废中奖」「奖品增删改」，
这些动作会改写现场已产生的数据，与「工作人员只干日常活」的定位冲突，故一并收回。

**权限只在服务端校验**。前端隐藏菜单只是少给人看，不构成安全边界：
工作人员的账号即便手动拼出 `/admin/data/reset` 并发起请求，也会被 `@PreAuthorize` 拦下返回 403。

**现场账号怎么建**：超管登录 →「设置 → 用户管理」→ 新增，填写姓名、手机号（登录账号）、初始密码、
**身份（管理员 / 签到台 / 抽奖台 / 兑奖台，可多选）**。该页面提供列表、建号、编辑（姓名/手机号/身份）、
重置密码、启用/停用、删除，不暴露部门/岗位表/自由勾角色/导入导出；身份白名单由后端 `StaffRoleGuard` 校验。
其中「管理员」身份只有内置超管（`user_id = 1`）能授予或收回，内置超管账号不可停用/删除，
自己也不能取消自己的管理员身份，避免把系统锁死。
普通角色与岗位账号都没有该菜单与接口权限（`kcon:staff:*`），看不到也调不通。
菜单与四个身份角色由基线 `sql/kcon_menu.sql` 与 `sql/00-ry-base.sql` 建立（RuoYi 原生「系统管理」仍保持隐藏）。

**工作人员不能自助改密**：个人中心不显示「修改密码」，后端 `PUT /system/user/profile/updatePwd`
对所有岗位工作人员直接拒绝；改密只能由超管在「设置 → 用户管理 → 重置密码」完成。
（避免现场人员把统一口令改成只有自己知道的值，导致交接班后无人能登录该账号。）

**清场的双重校验**：除权限码外，还要求输入当前登录人本人的密码（BCrypt 比对 + 连续错 5 次锁 30 分钟）。
详见 `docs/03-接口设计.md` 4.7 节。

> **核验强度分级（重要）**：签到环节凭**观众手机截图**发胸牌，截图可被伪造/转发，但胸牌为通用低价值物料，风险可接受；**兑奖环节一律不认截图**，必须走 FR-23 的「端口号 + 手机号」双因子系统核验。

## 5. 关键流程

### 5.1 签到流程（观众自助）
```
观众到前台，扫签到台水牌二维码（自己手机）
        ↓
输入完整 11 位手机号
   ├─ 命中 1 人 → 展示身份 → 点「确认签到」
   └─ 命中 0 人 → 提示联系工作人员（走人工/嘉宾通道）
        ↓
分配随机端口号（不放回）→ 手机成功页大字展示 + 截图提示
        ↓
观众截图 → 出示给前台工作人员 → 工作人员目视确认 → 在统一签到表上打钩 → 发放胸牌
```

> **风险说明**：本环节以截图作为已签到的凭据，截图可伪造/转发。因胸牌为通用物料、价值低，接受此风险；**兑奖环节不适用此做法**，见 5.3。

### 5.2 抽奖流程
```
主持人在管理端「抽奖控制台」选场次（上午/下午）→ 大屏轮询到变化后同步切换
        ↓
   控制台点「抽一档」→ 后台锁定此刻抽奖池 → 把当前档位剩余名额一次抽完
        ↓
   大屏逐个揭晓：第 1 / N 位 → 端口号滚动 → 定格 + 显示姓名 + 公司
        ↓
   全部揭晓完停在汇总页（本档全部中奖者 + 端口号）
        ↓
   ├─ 人都在场 → 点「抽下一档」继续抽下一个等级
   └─ 有人不在场 → 点该位的「撤回」→ 名额退回本档，再点「抽下一档」补抽缺的那位
```

> 抽奖粒度：**一次点击 = 抽完一档**（不是一个人）。滚动特效是「一个人一个人的端口号滚动」，
> 属于揭晓动画，不代表一次只抽一个人。

### 5.3 兑奖核验流程（双因子 · 不认截图）
```
领奖人到兑奖台，口头报【端口号 + 完整 11 位手机号】
        ↓
管理端核验页输入 端口号 + 手机号
        ↓
   系统校验：
   ├─ 端口号未发放 → 拦截：「该端口号未发放，可能为伪造截图」
   ├─ 端口号有效但手机号不匹配 → 拦截：「手机号与持号人不符」
   └─ 两者匹配 → 显示 姓名/手机掩码/公司/邮箱/奖项/状态
        ↓
   工作人员目视核对姓名，一致 → 点「已领取」→ 发奖
        ↓
   写入发放日志（谁在什么时候发放了哪个号的奖品，kcon_benefit_grant type=PRIZE）
```

> 领奖人即便出示截图，工作人员也**必须以系统核验结果为准**，截图仅作参考。

## 9. 约束与依赖

1. 运行环境：全栈 Docker Compose（含 JDK 17 + SpringBoot、MySQL 8.0、Node.js 构建 + Nginx），宿主机只需 Docker。
2. 名单质量依赖：必须提供**姓名 + 手机号 + 渠道来源**（渠道必须已配置映射，权益与抽奖资格由映射带出），缺手机号无法自助签到；**公司、邮箱、「职务/年级」可为空**，不阻塞签到，可在管理端补录。
3. **网络依赖**：观众用自己手机经公网扫码签到，不再受会场 WiFi 带机量与 AP 隔离限制。剩余风险点是**会场到服务器的公网质量**，建议会前实测。
4. 奖品：**档位与数量**入库并由后台配置；**具体实物方案不录入**，现场按实际情况发放。
5. **构建与部署分离**：镜像在本地构建（`--platform linux/amd64`），服务器只 `docker load` 与 `up -d`。服务器出网受限，不执行 `mvn` / `npm` / 拉基础镜像。

## 11. 系统可迁移（换电脑部署）

### 11.1 目标
整套系统（程序 + 数据 + 配置）能从一台电脑**完整迁移**到另一台电脑，新机器上不丢数据、不改代码即可运行。

### 11.2 迁移需要搬的三样东西
| 类别 | 内容 | 迁移方式 |
|---|---|---|
| **数据** | `./data/mysql`（MySQL 数据目录） | 随项目目录一起打包拷贝 |
| **程序** | 四个 Docker 镜像（可由新机重建） | 拷镜像 tar 包，或在新机 `docker compose build` |
| **配置** | `.env`（端口、密码、`LAN_IP`） | 一个文件，只改 IP/端口 |

### 11.3 迁移方式：**Docker Compose 一键迁移（已确认）**

采用 **方案 B · Docker Compose**，详细实施见《04-部署运行》。

1. 一份 `docker-compose.yml` 定义 **四个容器**：MySQL、后端、Web（统一入口，托管管理端 + 签到 H5 + 抽奖大屏三套静态资源并反代 API）。
2. 数据落在**宿主机目录** `./data/mysql`（不是匿名卷，便于直接拷走）。
3. 配置集中在 `.env`（端口、密码、`LAN_IP`），后端数据库连接全部由环境变量注入，不硬编码。
4. 迁移 = 打包项目目录（含 `data/`）→ 新机解压 → `docker compose up -d`。
5. 现场只暴露一个端口（默认 80），三端同源，无跨域。
6. 同一份镜像与编排**可原样搬到公网服务器**（第二期只需换 `.env` + 加 HTTPS 层），无需改代码。

### 11.4 设计要求（无论哪种方案都要满足）
1. **配置外置**：数据库地址/账号/密码集中在 `application-druid.yml`，不硬编码在代码里。
2. **无本机绝对路径依赖**：所有资源路径用相对路径或配置项。
3. **数据一键备份/恢复**：管理端提供「导出全量数据」按钮（生成 .sql 下载），新机可导入。
4. **端口号池可重建**：`kcon_port_pool` 由脚本生成，新机导入即恢复。
5. **幂等初始化**：首次启动自动建表/初始化场次与奖品档位（或提供一键初始化脚本）。

### 11.5 验收
| 编号 | 验收项 | 通过标准 |
|---|---|---|
| AC-11 | 数据导出 | 管理端能导出全量数据 .sql 文件 |
| AC-12 | 跨机迁移 | 全新电脑装好 Docker，解压项目 + `docker compose up -d` 即完整跑起来，数据一致 |
| AC-13 | 断网可用 | 会前已完成镜像构建，现场无外网仍能签到与抽奖 |
| AC-14 | 可重复启动 | `docker compose down` 后再 `up`，数据与端口号不变 |

### 13.1 变更项一：管理端账号口令

**问题定义**
管理端沿用 RuoYi 开源默认账号 `admin / admin123`。该口令随开源代码公开，而实例现在
80 端口对公网可达，任何人猜到默认口令即可登录管理端，进而清场数据、导出全库、
查看中奖信息。属必须立即处置的高危项。

**概念与口径**
- 账号 = `sys_user.user_name`；口令 = `sys_user.password`
- 口令落库形态是 **BCrypt**（`$2a$10$...`），不是明文也不是 MD5。手工算哈希极易算错，
  因此改口令必须走应用自身的 BCrypt 路径，不手写 SQL 拼哈希
- RuoYi 没有「修改登录账号」的界面入口，账号只能改库

**需求**

| 编号 | 需求 |
|---|---|
| FR-42 | 管理端账号由 `admin` 改为 `KconLucky` |
| FR-43 | 口令改为 `Kcon2026Aa.`，以 BCrypt 落库 |
| FR-44 | 改动覆盖三处：线上库（立即生效）、`sql/00-ry-base.sql` 种子（新装即生效）、文档与脚本里的默认账号表述 |
| FR-45 | **强制旧会话下线**：清空 Redis 中的登录态。改名后旧 token 仍带 `userName=admin`，若不清空，已登录会话在 token 到期前仍可用，等于改口令没生效 |

**不做清单**

### 13.2 变更项二：数据管理页导航失败

**问题定义**

4. 前端无任何硬编码 `/data` 跳转，排除菜单改版的遗留引用

**已确认根因**（2026-10-15 于公网实例复现，浏览器控制台报错）

```
Error: Cannot find module './kcon/data/index'
    at http://123.56.72.135/admin/static/js/app.9f697c2d.js
```

| 证据 | 结论 |

| `git check-ignore -v` 命中 `.gitignore:21:data/` | 确认被误排除 |
| 公网实例控制台 `Cannot find module` | 新克隆的仓库缺文件，webpack 动态 import 的 context 里没有它 |
| 侧边栏 href 实测为 `/admin/setting/data` | 路由与菜单配置本身正确（H2 排除） |

### 13.2.1 路由重名（FR-50）

**事实**：路由名默认由 `path` 推导（`capitalize(path)`），全量比对后有**两处**与 RuoYi 自带路由撞名：

| 菜单 | 推导名 | 撞上 |
|---|---|---|
| 3006 数据管理（`data`） | `Data` | `ruoyi-ui/src/router/index.js` 内置字典页路由 `name: 'Data'` |
| 3100 日志（`log`） | `Log` | RuoYi 自带菜单「日志管理」（menu_id 108，`path=log`） |

vue-router 的 name 映射只保留先注册的一个，重名会让按 name 跳转与缓存判定变得不可预期。

| 编号 | 需求 |
|---|---|
| FR-50 | 为这两处显式配置 `route_name`（`KconDataManage` / `KconLog`），消除与自带路由的撞名；URL 不变 |

**反向约束（不得违反）**：`route_name` 需避开现有 8 个页面组件名
（`KconDashboard`/`KconAttendee`/`KconDrawConsole`/`KconVerify`/`KconWinner`/
`KconVerifyLog`/`KconPrize`/`KconData`）。

- **当前**：页签栏已关闭（`settings.js` 的 `tagsView: false`，`TagsView` 组件已移除），
  `cachedViews` 不含任何真实组件名，**任何页面都不会被缓存**，每次进入都重新加载。
- **将来若重新开启页签栏**：`tagsView` 会把**路由名**写入 `cachedViews`，
  而 `AppMain` 的 `<keep-alive :include="cachedViews">` 按**组件名**匹配。
  届时两者一相等就等于开启页面缓存，返回时会看到旧数据（如数据管理页
  已输入的「清场」确认词仍在，仍需在弹窗二次确认，但不必重输）。
  所以命名须提前避开现有组件名。

> **只消除了 name 层，path 层仍有重叠**：3100 与 108 的 `path` 同为 `log`。
> 请勿在「菜单管理」界面编辑 3100——`checkRouteConfigUnique` 的「根目录路由冲突」
> 分支会因 108 同为 `path=log` 而判重拦截，导致改任何字段都存不进去
> （108 反向不受影响，可正常编辑）。需要调整 3100 时改 `sql/kcon_menu.sql` 或走 SQL。

**迁移要求**（2026-10-23 起已过时）：增量迁移脚本模式已废弃，`route_name` 已直接写入基线 `sql/kcon_menu.sql`；已部署库结构变更统一走「删 data/mysql 重建」（见 `docs/04` §9.3）。
