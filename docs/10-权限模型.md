# KCon 2026 权限模型（权威说明）

**适用版本**：v0.4.1 及以上
**结论先行**：权限分三层——① 登录认证；② 功能权限（菜单/接口权限点）；③ 数据范围。
现场账号只分四种身份：**管理员 / 签到台 / 抽奖台 / 兑奖台**，其它角色（如 `common`）是 RuoYi 遗留，不参与现场使用。

---

## 1. 三层权限

| 层 | 载体 | 生效位置 | 不满足时 |
|---|---|---|---|
| 认证 | JWT（登录后写 Redis `login_tokens:*`） | 所有 `/admin/**` 接口 | 401，跳登录页 |
| 功能权限 | `sys_menu.perms` + `sys_role_menu` | 后端 `@PreAuthorize("@ss.hasPermi('...')")` | HTTP 200 + `code=403`，前端提示「当前操作没有权限」 |
| 数据范围 | `sys_role.data_scope` | 列表查询 | 本项目四个身份全部为「全部数据」（`1`），不做部门隔离 |

两个关键事实：

1. **菜单可见 ≠ 有权限**。`sys_menu.visible='1'` 只影响侧边栏是否显示，接口仍然按权限点校验；反过来，只要权限点够，直接调接口也能成功。
2. **权限在登录时固化进 token**。改角色、改角色授权之后，该账号必须**重新登录**才生效（「设置 → 用户管理」编辑身份时后端会主动吊销对方旧令牌）。

---

## 2. 身份与菜单矩阵

`role_id` 由初始化脚本固定（新装基线）：

| 身份 | role_id | role_key | 能看到的菜单 |
|---|---|---|---|
| 管理员（内置超管角色） | 1 | `admin` | 全部 36 个 KCon 菜单 |
| 普通角色（遗留，勿用） | 2 | `common` | 11 个（无账号绑定，保留仅为兼容） |
| 签到台 | 3 | `kcon_checkin_staff` | 数据总览、参会名单、日志（权益发放/中奖日志/奖品发放） |
| 抽奖台 | 4 | `kcon_draw_staff` | 数据总览、参会名单（只读）、抽奖控制台、日志 |
| 兑奖台 | 5 | `kcon_verify_staff` | 数据总览、参会名单（只读）、兑奖核验、日志（可导奖品发放） |

三岗位**都看不到**：设置类（奖品设置/渠道来源/用户管理/数据管理）、中奖作废、其它岗位的核心操作。这是最小授权的刻意设计，不是故障。

## 3. 接口 → 权限点对照

### 3.1 匿名接口（无需登录）

| 接口 | 说明 |
|---|---|
| `POST /app/checkin/query`、`/submit`、`/lookup` | 观众签到；只接受完整 11 位手机号 |
| `GET /app/screen/status` | 抽奖大屏轮询；只读，只下发端口号/奖项/时间 |
| `POST /login`、`GET /captchaImage` | 登录与验证码 |

### 3.2 管理端接口

| 模块 | 接口 | 权限点 |
|---|---|---|
| 名单 | `GET /admin/attendee/list`、`/dashboard`、`/qrcode`、`/qrcode.png` | `kcon:attendee:list` |
| | `GET /admin/attendee/{id}` | `kcon:attendee:query` |
| | `POST /admin/attendee` | `kcon:attendee:add` |
| | `PUT /admin/attendee`、`/phone` | `kcon:attendee:edit` |
| | `DELETE /admin/attendee/{ids}` | `kcon:attendee:remove` |
| | `POST /admin/attendee/import`、模板 | `kcon:attendee:import` |
| | 导出（统一签到表等） | `kcon:attendee:export` |
| 签到明细导出 | `POST /admin/data/export` | `kcon:attendee:export` |
| 权益发放 | `POST /admin/benefit/grant` | `kcon:benefit:grant` |
| | 权益发放日志 | `kcon:benefit:list` / 导出 `kcon:benefit:export` |
| 奖品 | 奖品设置列表 | `kcon:prize:list`，增/改/删 `add/edit/remove` |
| 渠道来源 | 映射列表 | `kcon:channel:list`（下拉另允许 `kcon:attendee:list`） |
| | 增/改/删 | `kcon:channel:add/edit/remove` |
| 抽奖 | 控制台状态 `GET /admin/draw/status` | `kcon:draw:query` |
| | 抽奖 `POST /admin/draw/draw`、切场次 `/session` | `kcon:draw:operate` |
| | 场次查询 `GET /admin/session/list` | `kcon:session:list` |
| | 大屏设置（赞助商等）`/admin/draw/setting` | `kcon:draw:query`（读）/ `kcon:draw:operate`（写） |
| 中奖 | 中奖日志 `GET /admin/verify/winners` | `kcon:winner:list` |
| | 作废单条 `POST /admin/verify/void/{winnerId}`、撤回最近一档 `POST /admin/draw/void-batch` | `kcon:winner:void` |
| 兑奖 | 核验查询 `POST /admin/verify` | `kcon:verify:query` |
| | 确认发放 `POST /admin/verify/receive` | `kcon:verify:receive` |
| 核验日志 | 查询 | `kcon:verify:query` |
| 奖品发放日志 | 列表 | `kcon:prizegrant:list`，导出 `kcon:prizegrant:export` |
| 账号管理 | 列表 / 建号 / 编辑 / 重置密码 / 删除 | `kcon:staff:list/add/edit/resetPwd/remove` |
| 数据清场 | `POST /admin/data/reset` | `kcon:data:reset` **且** 再校验操作人本人密码 |
| 数据迁移 | 导出/恢复 | `@ss.hasRole('admin')`（不挂权限点，直接要求管理员角色） |

## 4. 账号管理规则（「设置 → 用户管理」）

由 `StaffRoleGuard` 统一收敛：

1. **登录身份是手机号**（11 位，`1[3-9]` 开头），`user_name` 只是内部标识，后端自动生成；
2. **身份只能从四个 key 里选**：`admin` / `kcon_checkin_staff` / `kcon_draw_staff` / `kcon_verify_staff`，可多选（一人多岗）；
3. **只有内置超管（user_id=1）能授予或收回「管理员」身份**，防止普通管理员批量造超管；
4. 岗位账号**不能自助改密**（密码由管理员统一设置），管理员不受限；
5. 编辑身份会立即吊销目标账号旧令牌，要求重新登录。

### 「管理员身份」账号的权限口径（v0.4.1 修复）

- RuoYi 原逻辑：只有 `user_id=1` 才算超管，并且在聚合权限时**跳过 `role_id=1`**；
- 现场允许给其他账号授予管理员身份，于是 v0.4.1 之前这类账号**权限集为空**，登录后每个页面都提示「当前操作没有权限」；
- v0.4.1 起：账号只要绑定了 `role_id=1`，即按全量权限（`*:*:*`）处理，与内置超管等效。

## 5. 现场排障：出现「当前操作没有权限」

后端日志会给出一行确凿证据（按下面的命令取）：

```bash
docker logs kcon-backend --since 2h 2>&1 | grep "权限校验失败"
# 例：请求地址'/admin/attendee/list',权限校验失败'Access Denied'
```

然后按「接口 → 权限点」对照表判断缺哪个权限，再用 SQL 确认账号实际绑了什么：

```bash
set -a; . ./.env; set +a
docker exec -e MYSQL_PWD="$MYSQL_ROOT_PASSWORD" kcon-mysql mysql -uroot kcon_lucky -e "
SELECT u.user_id,u.phonenumber,u.status,GROUP_CONCAT(r.role_id),GROUP_CONCAT(r.role_key)
  FROM sys_user u
  LEFT JOIN sys_user_role ur ON ur.user_id=u.user_id
  LEFT JOIN sys_role r ON r.role_id=ur.role_id
 WHERE u.del_flag='0' GROUP BY u.user_id;

SELECT role_id,COUNT(*) menus FROM sys_role_menu GROUP BY role_id ORDER BY role_id;"
```

期望的菜单数：`role 1=36`、`role 2=11`（遗留）、`role 3=11`、`role 4=10`、`role 5=10`。
数量不对说明菜单基线没执行完整（已有数据不会自动重跑初始化脚本）。

### 现象 → 原因速查

| 现象 | 最可能原因 | 处理 |
|---|---|---|
| 新建「管理员」账号处处 403 | 镜像 < v0.4.1 的权限聚合缺陷 | 升级到 v0.4.1，重新登录 |
| 新建岗位账号侧边栏很少 | 设计如此（最小授权） | 无需处理；需要更多权限就加绑定第二个岗位 |
| 改了角色授权但对方没变化 | 权限在 token 里 | 让对方退出重登 |
| 侧边栏有入口、点进去 403 | 角色有菜单但缺对应按钮权限 | 按对照表补授权或改角色 |
| 侧边栏出现「系统管理/系统监控」等原生菜单 | 菜单初始化脚本没执行 | 重跑 `sql/kcon_menu.sql` 的隐藏段（保留 menu 1 + 106） |
| 登录直接 401/跳登录页 | 账号停用 / 令牌被吊销 / 改过 `TOKEN_SECRET` | 查 `sys_user.status`，或让用户重登 |
| 岗位账号想自己改密码被拒 | 设计如此（密码统一管理） | 由管理员在用户管理里重置 |

## 6. 已知取舍（属设计，不是漏洞）

1. **大屏与签到免登录**：大屏只读、只下发端口号；签到只接受完整 11 位手机号，`submit` 还要与名单等值匹配。
2. **不按 IP 限流**（v0.4.0 起）：现场共用出口 IP，按 IP 分桶会误伤签到；若长期公网暴露，应按手机号/设备维度重建限流。
3. **数据范围不做部门隔离**：四个身份都是「全部数据」，避免现场查询被部门维度挡掉。
4. **角色 2（`common`）保留但不可用**：仅 11 个菜单、无账号绑定；不要用它建号，需要新身份请用岗位三选一或管理员。
