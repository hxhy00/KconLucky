**状态**：已实现（阶段 1–6 已落地；2026-10-19 复核：代码与四个构建通过，现场数据验收待执行；同日完成匿名报文最终收口；导入模板改为 8 列，`ticket_type` 语义改为「权益类型」，`draw_eligible` 仍为唯一显式资格列，详见 spec 008；签到端只认完整 11 位手机号，submit/lookup 返回 `ticketType` 供成功页/找回页展示）
**基准**：修订 `01-需求规格.md` FR-37 / AC-05；关闭 `01-需求规格.md` §10 待确认项 3
**日期**：2026-10-16

## 1. 问题定义

- **谁在什么场景**：KCon 2026 现场抽奖。名单由票务侧汇总，包含 **7 类票源渠道**（`S`嘶吼 / `T`TGO / `C`崔牛会 / `H`活动行 / `D`对公 / `G`赠票 / `V`嘉宾VIP媒体）与多个票种（散客票 / 早鸟票 / 标准票 / 合作渠道票 / 对公票 / **赠票** / **嘉宾票**）。
- **问题**：现行抽奖池 = 「已签到 ∩ 未中奖」（FR-37），**不看票种、不看渠道**。赠票与嘉宾票、VIP/媒体票持有人同样会签到并被抽中。
- **为什么是问题**：赠票/嘉宾票是**零付费**票源，其持有人参与面向购票观众准备的奖品抽奖，对**真正花钱买票的观众不公平**；同时奖品总量有限，被非付费票源稀释。
- **现状凑合方式**：`01-需求规格.md` §10 待确认项 3 挂账为「当前默认全部参与」，原始需求文档建议「G赠票/V嘉宾也进抽奖池，如需排除请告知」。现决策：**排除**。

## 2. 概念模型

### 2.1 术语

| 术语 | 定义 |
|---|---|
| **真正买票者** | 票种非「赠票」「嘉宾票」，**且**渠道标识非 `G`、`V` 的参会人。见下 2.2 判定口径。 |
| **付费票种白名单** | `散客票` / `早鸟票` / `标准票` / `合作渠道票` / `对公票` 及票务侧实际使用的其它**付费**票种名。 |
| **抽奖白名单** | 参与抽奖的票种集合由**系统参数**配置（见 6.2），默认值即上述付费票种白名单。 |
| **签到** | 与抽奖解耦：非买票者**照常签到、照常拿端口号、照常领胸牌**，仅不参与抽奖。 |

### 2.2 判定口径（**三层，与关系，全部满足才算可抽**；2026-10-16 用户确认）

```
drawEligible = (名单显式列「是否参与抽奖」= 「是」)          ← 第 5 必填列，空/无法识别 = 否
             AND (channel 非 G 且 非 V)                      ← 渠道黑名单（系统参数，实时）
             AND (ticketType 不含任一免费关键字)              ← 票种关键字黑名单（系统参数，实时）
```

**为什么加名单显式列**（2026-10-16 用户确认）：

- 名单由票务侧汇总，「是否参与抽奖」是票务侧的**显式事实**，不由票种/渠道推导——票务侧最清楚哪些人是真正的购票者（如内部工作票、特殊合作票等票种/渠道口径覆盖不到的情况）。
- 导入为**第 5 必填列**，只有显式填「是」才具备基础资格；**留空或无法识别一律按「否」入库**（fail-safe：漏填只会让持有人失去抽奖资格，不会把该被排除的人放错进池）。
- 落库为 `kcon_attendee.draw_eligible`（`TINYINT`，见 6.5），名单页可展示、可筛选、可手工改单条，导入后行为稳定，不受票种后续补录修改的影响。

**为什么用「票种关键字黑名单」而不是白名单做默认**：

- `ticket_type` 是**自由文本**（`02-数据库设计.md` §3.8 明确「不做枚举校验」），票务侧随时会写「VIP票」「VIP/嘉宾/媒体票」「特邀嘉宾票」等新写法，**白名单会漏**——漏掉的后果是**该被排除的人进了池子**，是「违规者中奖」的严重错误。
- 黑名单的失效模式相反：**不认识的票种名默认视为付费**，最坏后果是「本该排除的人只被渠道拦下一半」。渠道 `G`/`V` 是**单字母枚举**（`01-需求规格.md` §3 术语表），可靠度高，能拦住绝大多数。
- 因此**默认策略 = 显式列（硬性）+ 渠道黑名单（硬性）+ 票种关键字黑名单（模糊）**；同时**提供系统参数**供会前按实际票种收敛口径（见 6.2）。

### 2.2.1 显式列与系统参数的优先级（2026-10-16 用户确认：**参数优先，列作数据来源**）

- 池计算时**系统参数黑名单实时判定、当场生效**：改参数可随时把已导入的人拦下（FR-A3）。
- 名单显式列是**基础资格**：列=「否」的人无论参数怎么改都不进池；参数**只能进一步排除**，不会把显式列排除的人重新放进来。
- 两个口径对同一人重复命中不重复计数。

### 2.3 默认排除关键字（仅在票种**包含**这些子串时排除）

`赠` / `嘉宾` / `VIP`（大小写不敏感）/ `媒体` / `免费` / `邀请`

> 「赠」一字同时覆盖「赠票」「赠送票」「嘉宾赠票」。

### 2.4 状态机（不变）

```
未签到 ──签到──> 已签到（持有端口号，非买票者不进抽奖池）
                              │
                    [买票者] ─┴─> 抽奖池 ──抽中──> 已中奖 ──核验──> 已领取
                                                        └─作废─> 已作废（号回池）
```

非买票者**不到达抽奖池**这一环，其余流程完全一致。

## 4. 需求规格

### 4.1 抽奖池过滤（核心）

- **FR-A1**：抽奖池口径修订为

  ```
  池 = 此刻已签到（当日） ∩ 未中奖 ∩ 真正买票者
  ```

  判定实现位置：`KconDrawServiceImpl.calcPool()` 是**池的唯一计算入口**，改这里即同时覆盖抽奖执行与大屏/控制台的 `poolCount`（`screenStatus()` 复用同一方法）。

- **FR-A2**：过滤必须是**池计算的一部分**，不得只在抽奖执行时校验——否则控制台与签到看板的「可抽号数」会虚高，操作员会按错误人数判断节奏。

- **FR-A3**：参数变更（票种白名单）**当场生效**，不需要重启。

### 4.2 签到流程（**不拦截、不提示**）

- **FR-A4**：非买票者**照常签到**，照常分配端口号，照常领胸牌。不得以「不参与抽奖」为由拒绝签到。
- **FR-A5**：签到端**不得暴露抽奖资格**（2026-10-16 用户修订）。非买票者看到的内容与买票者**完全一致**：成功页文案、落款、找回结果一律不区分。理由：
  1. 签到/找回均为**免登录接口**，一旦回传资格标记或渲染差异文案，任何人都能自查「我在不在池里」，等于把筛选口径对外开放；
  2. 明示「您不参与抽奖」等于当面告知「您的票是白来的」，是引发现场争执的直接来源；
  3. 争执处理放在兑奖台，由工作人员按核验结果（未中奖）依既定话术回应，不在自助端预留话题。

  **实现约束**：`POST /app/checkin/submit` 与 `GET /app/checkin/lookup` 的响应体**均不含** `drawEligible`；`KconCheckinServiceImpl` 不引用 `DrawEligibility`。2026-10-19 最终收口：`GET /app/checkin/query` 不再返回 `ticketType` 与 `channel`——两者分别是票种/渠道黑名单的直接输入，按「报文里有没有这个字段」的判据都属于泄露面。判定结果只存在于服务端，供抽奖池与统计使用。同日 `ticket_type` 语义改为「权益类型」；`submit` / `lookup` 可返回 `ticketType` 供成功页/找回页展示，但 `query` 仍不返回，`drawEligible` 所有接口都不返回。

### 4.3 兑奖核验（**不新增校验**）

- **FR-A6**：兑奖核验维持「端口号 + 完整 11 位手机号」（FR-41），**不加入票种校验**。理由：能中奖的人必然已是买票者，核验时重查票种是重复防线，且会引入「票种被后改」这类新的失败面。

### 4.4 可观测性（现场必备）

- **FR-A7**：管理端抽奖控制台必须显示**被排除人数**，否则「今日已签到 300、可抽号数 180」会被当成 bug 报上来。
- **FR-A8（黑箱边界）**：不暴露口径的范围仅限**观众可达的界面与免登录接口**。管理端（需登录 + 权限点）允许出现差额与资格明细，但文案取中性措辞，不出现「赠票 / 嘉宾 / VIP」等具体票源名——口径只写在服务端配置里，界面只是"有差额"。

  | 面 | 是否可见资格/差额 | 依据 |
  |---|---|---|
  | 签到大屏（免登录展示） | 否，只有 `poolCount` | spec 005 已收紧 |
  | 签到 H5 成功页 / 找回结果 | 否，与买票者完全一致 | FR-A5 |
  | `submit` / `lookup` 响应体 | 否，无 `drawEligible` 等字段 | FR-A5 |
  | 抽奖控制台 | 差额（中性文案） | FR-A7 |
  | 名单页「参与抽奖」列/筛选/补录 | 是 | 需登录，供操作员回答「他为什么没进池」 |

- **FR-A9（现场话术）**：非买票者若到兑奖台质问「我怎么没被抽中」，工作人员按**未中奖**口径回应，不解释筛选规则：

  > 「抽奖是从当天现场签到的观众里随机抽取的，没有中奖是运气问题。您可以继续关注后面的抽奖轮次。」

  落地要求：
  - 兑奖核验页（`kcon/verify/index.vue`）在「已签到但尚未中奖」的结果旁，以中性小字提示话术方向（如「按未中奖口径回应，不解释抽取范围」），避免工作人员临场自创解释；
  - 工作人员培训材料只写"随机抽取"，**不写**排除规则；知道规则的人越少，口径越不容易漏。

### 4.6 已踩过的坑：字段不能靠"前端不展示"来保护

`screenStatus()` 是**管理端与免登录大屏共用**的方法（`DrawAdminController#buildStatus` 与 `DrawScreenController#status` 都调它）。首版把 `excludedCount` 直接放进该方法，注释还写着「大屏不消费该字段」——但字段照样躺在 `/app/screen/status` 的匿名响应里，任何人 `curl` 一次就能读到被排除人数，`checkedInToday − poolCount` 的差额含义也随之公开。

**结论（实现约束）**：

| 共享方法的调用方 | 处理 |
|---|---|
| 管理端 + 匿名端共用 | 只放"匿名可见也不构成泄露"的字段；敏感字段由管理端控制器**自行附加** |
| 仅管理端调用 | 可自由返回 |

判断标准是**报文里有没有这个字段**，不是**前端渲不渲染它**。这与 FR-A5 是同一类错误，只是位置从 service 换到了共享方法。

**同类收口（2026-10-19）**：`screenStatus()` 原先还返回 `checkedInToday` 与 `winnerCount`。`checkedInToday − poolCount` = 被排除 + 已中奖，匿名请求同样能反推口径。两者已移出 `screenStatus()`，改由 `DrawAdminController#buildStatus` 附加；匿名大屏只剩 `poolCount` 等展示字段。

### 4.5 不做清单

| 不做 | 理由 |
|---|---|
| 修改签到拦截逻辑 | 门票与奖品是两条独立规则，签到与否只影响胸牌 |
| 兑奖核验加票种校验 | 见 FR-A6 |
| 改动已发布的历史抽奖池口径 | 无历史数据 |
| 前端硬编码票种清单 | 必须走系统参数，见 6.2 |
| 名单导入时拦截免费票 | 免费票持有人也要签到 |
| 导入时跳过「是否参与抽奖」为空的行 | 空值按「否」入库（见 2.2），该人照常签到领胸牌；拦截会导致名单缺失、现场无法核验身份 |

## 5. 交互设计

### 5.1 管理端抽奖控制台（`ruoyi-ui/src/views/kcon/draw/index.vue`）

三项统计的**口径说明**补在标签下方（小字），避免误读：

| 标签 | 值 | 副说明 |
|---|---|---|
| 可抽号数 | `poolCount` | `按资格规则过滤后的可抽人数` |
| 今日已签到 | `checkedInToday` | 保持原样（**全部签到人数**，含非买票者） |
| 已中奖 | `winnerCount` | 保持原样 |

新增一行**排除提示**（`excludedCount > 0` 时才显示）：

```
今日已签到的观众中有 120 位不在本次抽奖范围内，抽奖池已自动过滤
```

> 管理端需登录，操作员知道差额存在即可排查「某人为何没被抽中」，**但文案不列出具体票源/票种名**（不写「赠票/嘉宾/VIP」），与 FR-A5 口径一致：口径只在服务端配置里，不在任何界面文案中。

### 5.1.1 名单页（`ruoyi-ui/src/views/kcon/attendee/index.vue`）

「参与抽奖」列、筛选器、补录开关**保留**（6.5 的落库目的就是"管理端可查可改"）。这是受限界面，不是泄露面：操作员需要它回答「这个人为什么没进池」。真正要守住的是**免登录的签到端**（FR-A5）。

### 5.2 大屏（`screen/src/App.vue`）

**不加**被排除人数（spec 005 已收紧大屏统计口径，运营数据不上大屏）。大屏现有 `poolCount`、`poolEmpty` 直接消费接口，**无需改动**。

### 5.3 签到 H5 成功页（`checkin-h5/src/App.vue`）

**买票者与非买票者文案完全一致，不新增任何分支**（2026-10-16 用户修订）：

- 成功页 / 已签到页 / 找回结果卡片，均按现有文案渲染，不读取也不展示抽奖资格。
- 后端 `submit` 与 `lookup` 的响应体**不返回** `drawEligible`（见 FR-A5）。
- 前端不因资格产生任何条件渲染差异——页面源码、响应报文里都查不到筛选口径。

### 5.4 状态覆盖

| 状态 | 表现 |
|---|---|
| 池中全为非买票者（`poolCount = 0`） | 复用现有「请先让观众签到」空池提示；`excludedCount > 0` 时副提示补一句「其中 N 位不在本次抽奖范围内」 |
| 系统参数缺失/为空 | 回退内置默认值（见 6.2），不报错 |
| 票种为 `NULL` | 视为付费（不被票种规则排除），仅受渠道规则约束 |

## 6. 架构设计

### 6.1 模块划分

| 模块 | 文件 | 改动 |
|---|---|---|
| 资格判定 | `DrawEligibility`（`ruoyi-system/.../service/impl/`，新增） | 三层判定 + 系统参数读取降级，**仅被抽奖池与统计引用**（签到服务不依赖它） |

### 6.2 配置项（复用 RuoYi 系统参数，无需迁移）

| 参数键 | 默认值 | 说明 |
|---|---|---|
| `kcon.draw.excludeChannel` | `G,V` | 渠道黑名单，逗号分隔 |
| `kcon.draw.excludeTicketKeyword` | `赠,嘉宾,VIP,媒体,免费,邀请` | 票种关键字黑名单，逗号分隔，大小写不敏感 |

> 参数读取失败（服务不可用）时降级为内置默认值——与 `kcon.sponsors` 的处理方式一致（`KconDrawServiceImpl#sponsors()`）。

### 6.3 关键决策与理由

1. **过滤放在 `calcPool` 而非 SQL 层**：`calcPool` 是唯一入口，`poolCount` 与 `draw()` 共用，改一处全覆盖；且过滤规则依赖可配置关键字，放 Java 层便于读取系统参数与写单测。
2. **`selectAllPorts` 改为联表**：把 `channel` / `ticket_type` / `draw_eligible` 一次性带出，避免对每个端口号调 `selectAttendeeById`（千人池 = 千次查询）。
3. **默认「显式列 + 双黑名单」而非白名单**：见 2.2，失效模式更安全（漏放而非错杀）。
4. **落库 `draw_eligible` 显式列**（2026-10-16 用户确认，修订本节原「不落库 isPaid 冗余列」）：这不是由票种推导的冗余列，而是票务侧的**显式事实**（第 5 必填列），语义独立于 `channel`/`ticket_type`；名单页可展示、可筛选、可手工改单条，导入后行为稳定。池计算仍按系统参数实时判定（参数优先，列作基础资格，见 2.2.1），不存在「改了票种但列没同步」的问题——列本来就不由票种推导。
5. **非买票者不被拦签到**：胸牌是通用物料、人人一致（FR-§10 项 6），拒绝签到会让现场产生无谓争执。
6. **漏填「是否参与抽奖」的行照常入库（按「否」）并单独计数**：不并入 `skipped`（它表示「没导入」），不拦截（见 4.5）。

### 6.4 接口契约增量

```
GET /admin/draw/status  → data 增加（管理端，需登录）
  excludedCount: number    // 今日已签到但不在抽奖范围内的人数
  checkedInToday: number   // 今日已签到总数（仅管理端）

                            响应仍不含 drawEligible
GET  /app/checkin/lookup  → 不变
GET  /app/checkin/query   → 响应移除 ticketType / channel（票种/渠道黑名单输入，2026-10-19）
  // 均为免登录接口，**不返回** drawEligible 等资格字段（FR-A5）

POST /admin/attendee/import  → data 增加（管理端，需登录）
  drawFlagMissing: number            // 漏填「是否参与抽奖」的行数（按「否」入库）
  flagMissingDetails: [{row, reason}] // 漏填行号明细（上限 20 条）
```

### 6.5 数据模型增量

```sql

`draw_eligible` tinyint NOT NULL DEFAULT 0
  COMMENT '是否参与抽奖：1=是 0=否（导入第 5 必填列，留空/无法识别按「否」入库）'
```

- 全新库：`kcon_lucky.sql` 已含该列；**已有库需手动执行 `kcon_migrate_v3.sql`**。
