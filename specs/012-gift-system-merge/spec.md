# Feature Specification: 赠票系统并入现有系统（模块化）

**Feature Branch**: `feature/012-gift-system-merge`

**Created**: 2026-10-26

**Status**: Draft（架构决策规格；不建议在本次大会前实施）

**Input**: 用户提问：赠票系统能不能直接集成到现有 KconLucky 系统里，作为一个模块？

## 背景

当前两套系统已经按「上下游」方式上线：

| 系统 | 职责 | 现状 |
|---|---|---|
| KconLucky | 名单、签到、端口号、抽奖、兑奖 | Java + MySQL + Vue，已有公网部署 |
| gift-system | 渠道 → 推荐人 → 接收人分发、审批、邮件 | Python + SQLite，独立容器，80 反代路径挂载 |

两套系统通过「导出已审批接收人 CSV → 本系统名单导入」交接。v1 的代价是：两套登录、两次操作、一次人工交接。

本规格回答一个问题：**能否把赠票能力合并进 KconLucky，作为一个模块，而不是独立系统？**

## 可行性结论

**能，但不是「把 Python 目录挂进去」这种直接集成。**

- 两套技术栈不同（Python/SQLite/模板 vs Java/MySQL/Vue），无法作为代码模块直接嵌入；
- 可行路径是**把赠票领域移植进 KconLucky**：新建业务表、Controller/Service、Vue 管理页、公开注册页与审批页、邮件服务，复用现有登录、权限、Redis 限流、Quartz、审计；
- 移植范围约为：14 张表中的 10 张（签到/签到员/外部同步相关表不需要）、24 个接口中的约 20 个、10 封邮件、2 个公开注册流程；
- 移植后可以取消 CSV 交接：最终审批通过时直接写入 `kcon_attendee`，由本系统统一名单。

**时机结论**：本次大会前不实施。当前侧车方案已上线且验证通过，大会前做跨栈移植风险远大于收益。建议大会结束后，以「是否长期保留赠票能力」为前提再启动。

## 方案对比

| 方案 | 做法 | 优点 | 代价 | 适用 |
|---|---|---|---|---|
| A. 侧车（当前） | 独立容器 + 80 反代 + CSV 交接 | 已上线、故障隔离、可独立回滚 | 两套登录、人工交接 | **本次大会** |
| B. 合并进本系统 | 领域移植到 Java/MySQL/Vue，取消 CSV | 单系统、单登录、无人工交接 | 重写 + 迁移 + 回归，周期长 | 大会后长期方案 |
| C. 只统一登录与数据 | 赠票保留独立服务，但管理员用本系统账号登录；接收人审批后直接写本系统名单 | 改动小于 B，消除重复登录与 CSV | 需跨系统鉴权与写名单接口 | 折中，可作为 B 的第一步 |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一个后台管两件事 (Priority: P1)

运营用同一个管理员账号登录 KconLucky，就能建渠道、审批推荐人/接收人，并查看赠票与现场签到数据，不再记忆两套账号。

**Why this priority**: 双登录与双后台是当前最主要的操作成本，也是合并的核心价值。

**Independent Test**: 用一个管理员账号登录后，能在同一侧边栏看到「赠票渠道」「赠票审批」与「参会名单」；无需求助第二套系统。

**Acceptance Scenarios**:

1. **Given** 管理员已登录 KconLucky，**When** 打开「赠票渠道」，**Then** 能创建渠道并触发审批员开通通知。
2. **Given** 渠道审批员收到开通邮件，**When** 使用本系统账号登录，**Then** 只能看到本渠道数据，跨渠道访问被拒。
3. **Given** 一名审批员被停用，**When** 其尝试登录，**Then** 被拒绝且旧审批链接失效。

---

### User Story 2 - 审批通过即进入现场名单 (Priority: P1)

接收人最终审批通过后，自动成为本系统参会人（按手机号去重），运营不再导出/导入 CSV。

**Why this priority**: 去掉人工交接，才能消除「少导了几个人」的风险。

**Independent Test**: 审批通过 1 名接收人后，本系统名单页立即出现该人，渠道/权益按映射带出，无需任何文件操作。

**Acceptance Scenarios**:

1. **Given** 接收人审批通过，**When** 查看参会名单，**Then** 该人已存在且手机号唯一。
2. **Given** 同一手机号已有名单记录，**When** 另一渠道再次审批通过，**Then** 更新既有记录并提示归属冲突，不产生第二条。
3. **Given** 渠道未配置映射，**When** 审批通过，**Then** 按明确规则处理（阻止并提示补映射，或落到默认权益），不得静默写错权益。

---

### User Story 3 - 公开注册与审批链接保持不变 (Priority: P2)

推荐人、接收人仍然免登录通过专属链接注册；审批链接仍然一次性、可邮件送达。

**Why this priority**: 这是外部用户体验，不能因为合并而要求外部人员注册本系统账号。

**Independent Test**: 打开推荐人/接收人注册链接可直接提交；审批链接一次性有效，使用后失效。

**Acceptance Scenarios**:

1. **Given** 渠道已创建，**When** 推荐人打开注册链接，**Then** 无需登录即可提交申请。
2. **Given** 审批链接已使用，**When** 再次打开，**Then** 提示已被使用。
3. **Given** 邮件发送失败，**When** 审批人从系统内操作，**Then** 审批仍可继续，不被邮件阻塞。

---

### Edge Cases

- **历史数据迁移**：SQLite 中已有的渠道/推荐人/接收人必须完整迁入，手机号/邮箱唯一约束冲突需先出清单人工处理。
- **审批员账号**：现有渠道审批员如何映射到本系统账号（新建用户 / 绑定角色 / 首次登录激活）需在实施前定稿。
- **重复手机号**：不同渠道推荐同一手机号，最终只保留一条名单，需记录归属冲突。
- **渠道映射缺失**：合并后没有「导入预检」这一步，必须在审批通过时拦截并提示，不能等到现场签到才发现。
- **邮件服务故障**：不得回滚审批事务；失败可重试，审批人可从后台继续操作。
- **大会进行中**：禁止热切换；合并只能在大會结束后、无存量写入的窗口执行。

## Requirements *(mandatory)*

### 新增需求（新增需求，待回写 `docs/01-需求规格.md`）

- **FR-M01**：系统 MUST 提供统一的管理员登录入口；管理员 MUST 能在一个后台完成渠道、推荐人、接收人、名单与签到数据的管理。
- **FR-M02**：渠道审批员 MUST 使用本系统账号登录，且只能访问所属渠道数据；跨渠道访问 MUST 返回拒绝。
- **FR-M03**：推荐人与接收人 MUST 继续以免登录专属链接完成注册，不要求创建本系统账号。
- **FR-M04**：接收人最终审批通过后，系统 MUST 自动创建或更新参会人记录（以手机号为唯一键），MUST NOT 依赖 CSV 人工交接。
- **FR-M05**：自动写名单前 MUST 校验渠道来源映射；未配置时必须明确拦截并提示，不得静默写入默认权益。
- **FR-M06**：审批、配额、单人上限、邮箱唯一、一次性令牌、被拒 7 天重申等既有业务规则 MUST 保持一致。
- **FR-M07**：邮件（开通、审批、注册码、签到通知、汇总）MUST 由本系统发送；单封失败 MUST 记录并不阻断审批。
- **FR-M08**：签到汇总类邮件 MUST 由后台定时任务触发（满 10 人或 30 分钟），不依赖用户请求。
- **FR-M09**：历史数据迁移 MUST 可重复执行、可核对；迁移前后渠道数、推荐人数、接收人数、已通过数 MUST 一致。
- **FR-M10**：合并后 MUST 保留回滚路径：旧侧车系统与数据在大會结束前不得删除。
- **FR-M11**：所有赠票相关管理操作 MUST 写入审计日志（操作人、对象、结果）。
- **FR-M12**：合并 MUST NOT 改变现有签到、端口号、抽奖、兑奖规则与数据口径。

### Key Entities

- **渠道**：名称、配额、单人上限、状态、绑定审批员。
- **推荐人**：归属渠道、状态、专属链接、已发放数量。
- **接收人**：归属推荐人/渠道、状态、注册码、审批时间。
- **审批令牌**：一次性、有归属、有有效期。
- **参会人**：本系统既有实体，手机号唯一，承载签到与抽奖资格。
- **渠道映射**：渠道来源 → 权益类型 / 是否参与抽奖，本系统既有实体。

## Success Criteria *(mandatory)*

- **SC-M01**：管理员只需 1 个账号、1 次登录即可完成赠票与现场两条业务线的日常操作。
- **SC-M02**：审批通过到名单可见的延迟不超过 5 秒，且无需任何文件操作。
- **SC-M03**：迁移后四类数量（渠道/推荐人/接收人/已通过）与迁移前差异为 0；冲突清单可逐条定位。
- **SC-M04**：赠票业务规则回归通过率 100%（配额、上限、邮箱唯一、令牌一次性、7 天重申）。
- **SC-M05**：邮件失败不影响审批成功率；失败邮件可在后台重试。
- **SC-M06**：合并后现有签到/抽奖/兑奖回归用例 100% 通过。
- **SC-M07**：回滚演练可在 30 分钟内恢复到侧车方案且不丢数据。

## Assumptions

- 合并在本届大会结束后启动，大会期间继续使用侧车方案。
- 管理员继续使用本系统账号体系；渠道审批员以本系统用户 + 渠道绑定实现。
- 公开注册页与审批页允许继续使用服务端渲染或独立轻量页面，不强制并入 Vue 管理端。
- 邮件继续使用企业微信邮，发件箱与凭据沿用现有配置。
- 赠票业务规模不超过 20 渠道 / 500 票，单库单表足够。
- 合并后不再保留「上游签到」概念，签到仍只由本系统负责。

## Out of Scope

- 大会前或大会期间的在线热切换。
- 重写签到、端口号、抽奖、兑奖逻辑。
- 为推荐人/接收人建立完整账号体系或 SSO。
- 保留两套系统长期双写。
- 赠票数据看板的大改版（只做必要的统计页）。
- 旧侧车系统的立即下线与数据销毁。

## 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 跨栈移植引入回归 | 高 | 以现有 552 个测试为业务规则基线，逐条对照 |
| 审批员账号映射不清 | 中 | P0 先定账号模型，再动代码 |
| 自动写名单放大错误 | 高 | 映射缺失硬拦截 + 冲突清单 + 可回滚 |
| 大会期间误切换 | 高 | 明确变更冻结窗口，侧车保留至大会结束 |
| 邮件发送失败 | 中 | 事务外发送、失败可重试、后台可手工补发 |
