# Feature Specification: 赠票资格分发与现场签到的系统边界

**Feature Branch**: `feature/011-gift-ticket-handoff`

**Created**: 2026-10-26

**Status**: 已实现（上游代码在 `gift-system/`，552 个测试通过；待部署上线）

**Input**: 用户决策：赠票系统（参考文件 `kcon-prod.zip`）只负责会前赠票资格分发；现场签到、抽奖、兑奖仍由本系统负责。v1 以「名单交接」快速上线，不做实时接口同步。

## 背景

当前存在两套系统：

| 系统 | 能力 | 部署形态 |
|---|---|---|
| 本系统（KconLucky） | 名单管理、自助签到、端口号、抽奖、兑奖、发放日志 | RuoYi + Vue + MySQL，已有本地与公网部署 |
| 赠票系统（kcon-prod） | 渠道 → 推荐人 → 接收人三级分发、两级审批、邮件通知、注册码 | Python + SQLite，独立进程 |

两套系统都有「签到」，但范式不同：

- 本系统：观众自助，手机号即身份，签到后分配抽奖端口号；
- 赠票系统：签到员扫注册码核验，不发端口号，不参与抽奖。

若两套同时签到，会出现**同一人两份签到记录、两套身份口径**。本规格明确：**签到唯一事实源是本系统**，赠票系统只产出「谁有资格来」。

## 系统边界

| 能力 | 赠票系统 | 本系统 |
|---|:---:|:---:|
| 渠道 / 配额 / 推荐人 / 接收人 | ✅ 负责 | ❌ 不感知 |
| 两级审批、一次性令牌 | ✅ 负责 | ❌ 不感知 |
| 邮件通知（M-01～M-08） | ✅ 负责 | ❌ 不发送 |
| 名单产出（已通过的接收人） | ✅ 导出 | ✅ 导入后成为唯一名单 |
| 现场签到 | ❌ 不启用 | ✅ 唯一事实源 |
| 端口号分配 | ❌ 无 | ✅ 负责 |
| 抽奖 / 中奖 / 作废 | ❌ 无 | ✅ 负责 |
| 兑奖核验 / 奖品发放 | ❌ 无 | ✅ 负责 |
| 权益发放 / 发放日志 | ❌ 无 | ✅ 负责 |

> 赠票系统注册码仅用于其邮件与扫码落地页展示，**不作为本系统签到凭证**；本系统签到仍以完整 11 位手机号为准。

## 数据交接（v1：文件交接）

| 项 | 约定 |
|---|---|
| 交接方向 | 单向：赠票系统 → 本系统 |
| 交接方式 | 赠票系统导出 CSV，人工在本系统「名单导入」上传 |
| 交接字段 | 姓名、手机号、渠道来源、公司、职位（空）、邮箱 |
| 导出范围 | 仅接收人状态为「已通过」的记录 |
| 去重口径 | 按手机号去重；同一手机号多条已通过记录时只保留一条，并把冲突明细单独输出供人工确认 |
| 导入模式 | 追加模式（按手机号更新已有记录，不重复插入） |
| 渠道口径 | 「渠道来源」必须与上游渠道名称完全一致；本系统须提前配置对应渠道映射 |
| 交接时点 | 会前 T-1 18:00 首次；活动当日 08:00 增量一次；之后按需 |
| 幂等 | 同一份文件重复导入不增加名单总数，仅更新时间与可编辑字段 |
| 失败处理 | 未配置映射的渠道导致整批拒绝；修正映射后重导，不产生部分落库 |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 会前把已审批的赠票名单交给现场系统 (Priority: P1)

市场/运营在赠票系统完成渠道建号、推荐人审批、接收人审批后，导出一份「已通过接收人」CSV，在本系统配置好渠道映射并导入，现场名单即为最终名单。

**Why this priority**: 没有这份名单，现场无法签到；这是两套系统唯一的交接点，决定上线是否可用。

**Independent Test**: 在赠票系统造 1 个渠道、1 个推荐人、1 个已通过接收人，导出 CSV，在本系统导入，名单页能查到该人且渠道/权益正确。

**Acceptance Scenarios**:

1. **Given** 赠票系统有 10 名已通过接收人，**When** 导出并导入本系统，**Then** 本系统新增/更新 10 人，手机号唯一，渠道与映射一致。
2. **Given** 本系统未配置某渠道映射，**When** 导入含该渠道的文件，**Then** 整批拒绝，提示缺失的渠道名，名单无任何变化。
3. **Given** 同一份 CSV 已导入一次，**When** 再次导入，**Then** 名单总数不变，不产生重复手机号。

---

### User Story 2 - 现场签到仍走本系统，赠票系统不参与 (Priority: P1)

观众到场后在签到 H5 输入完整手机号完成签到，获得端口号；赠票系统不创建签到员账号，也不对外提供签到入口。

**Why this priority**: 避免双写与身份冲突，是边界成立的核心。

**Independent Test**: 活动期间检查本系统签到记录增长，赠票系统签到记录为 0；本系统签到成功页正常显示端口号。

**Acceptance Scenarios**:

1. **Given** 名单已导入，**When** 观众在本系统签到，**Then** 产生一条本系统签到记录并分配端口号。
2. **Given** 活动进行中，**When** 检查赠票系统，**Then** 无签到员账号、无新增签到记录、现场不出现其签到入口。
3. **Given** 观众已完成本系统签到，**When** 再次查询，**Then** 返回原端口号，不重复分配。

---

### User Story 3 - 上线后核对交接结果 (Priority: P2)

运营在导入后核对行数、渠道与重复情况，并把结果留档，作为上线验收依据。

**Why this priority**: 交接是人工动作，必须有可核对的闭环，避免「少了几个人」直到现场才发现。

**Independent Test**: 导入完成后生成一张核对表：上游已通过数、导出行数、新增数、更新数、被拒渠道数、重复手机号数。

**Acceptance Scenarios**:

1. **Given** 上游已通过 120 人、去重后 118 人，**When** 导入，**Then** 核对表显示 118 行，差异说明 2 条冲突已单独列出。
2. **Given** 导入结果与预期不一致，**When** 重新核对，**Then** 能定位到具体手机号或渠道，不需要查库猜。

---

### Edge Cases

- **同一手机号出现在两个推荐人名下**：导出时只保留一条并输出冲突清单，人工确认归属后再导入。
- **接收人未填手机号**：导出时列为异常行并排除出交接文件（本系统以手机号签到，无手机号无法签到），由运营联系推荐人补齐后再导。
- **上游拒绝/作废发生在导出之后**：v1 不做同步；以导入时的状态为准，作废由本系统管理员手工删除（已签到/已中奖者按现有规则拒绝删除）。
- **渠道改名**：上游改名后需在本系统新增映射并重新导入；旧渠道存量名单不自动迁移。
- **邮箱必填而上游邮箱为空**：上游注册时邮箱必填，正常不会出现；若出现，导出时标记为异常行，不进入导入文件。
- **上游邮件服务不可用**：注册/审批仍可继续（邮件失败不阻断），但需在活动前完成发信验证。
- **场地网络中断**：本系统签到为本地部署，不依赖上游；交接文件可提前导入。
- **人数超过 500**：v1 以 500 为规模基线；超出需在导入前确认本系统端口池与名单上限余量。

## Requirements *(mandatory)*

### 沿用的现有需求（`docs/01-需求规格.md`）

- **FR-10 / FR-11**：名单导入支持 Excel/CSV、追加与替换模式。
- **FR-13.2**：名单支持按渠道、签到状态等筛选。
- **FR-34**：手机号是全场唯一主键。
- **FR-35**：导入模板 6 列，渠道来源映射是硬白名单，未配置渠道整批拒绝。
- **FR-36**：端口号 1–65535 不放回，签到后持久化不变号。
- **FR-01～FR-08**：签到端免登录、完整 11 位手机号、重复签到返回原端口号。
- **FR-18 / FR-23 / FR-24**：抽奖、兑奖双因子、奖品发放留痕。

### 新增需求（新增需求，待回写 `docs/01-需求规格.md`）

- **FR-G01**：赠票系统 MUST 支持导出「已通过」接收人为 CSV，字段固定为姓名、手机号、渠道来源、公司、职位、邮箱；职位允许为空。
- **FR-G02**：导出 MUST 按手机号去重；同一手机号对应多条已通过记录时，MUST 只输出一条并单独列出冲突明细（手机号、涉及推荐人、涉及渠道）；手机号为空的记录 MUST 列入异常清单并排除出交接文件。
- **FR-G03**：本系统 MUST 以追加模式导入交接文件；同一手机号更新既有记录，不得新增重复行。
- **FR-G04**：导入前 MUST 校验渠道映射；存在未配置渠道时 MUST 整批拒绝并列出渠道名，不得部分落库（沿用 FR-P12 严格模式）。
- **FR-G05**：签到唯一事实源 MUST 是本系统；活动期间赠票系统 MUST NOT 创建签到员账号，MUST NOT 向现场提供签到入口，其签到记录 MUST 为 0。
- **FR-G06**：同一份交接文件重复导入 MUST 幂等：名单总数不增加，仅更新可编辑信息。
- **FR-G07**：500 人规模的导出 + 导入 MUST 在 10 分钟内完成，且不要求人工改库。
- **FR-G08**：v1 的邮件真实投递 MAY 暂缓（二期接入企业微信邮，使用单一发件邮箱）；暂缓期间 MUST 提供可用的「邮件出箱」，让管理员/审批员能查看并复制审批链接，业务流程不得因未发信而中断。
- **FR-G08a**：邮件出箱 MUST 支持按模板筛选、查看邮件正文、复制其中的链接；仅管理员与审批员可访问。
- **FR-G09**：赠票系统的管理员 MUST 由「管理员账户管理」维护（新增、停用、删除、列表），MUST NOT 依赖写死在代码里的邮箱白名单；启用中的管理员 MUST ≤ 3 人；MUST 禁止停用/删除最后一个启用中的管理员；首次部署 MUST 能通过配置注入初始管理员。
- **FR-G10**：赠票系统的数据文件 MUST 每日备份，保留最近 7 天，备份失败可被发现。
- **FR-G11**：每次交接 MUST 产出一张核对结果：上游已通过数、导出行数、新增数、更新数、被拒渠道数、重复手机号数。
- **FR-G12**：v1 交接 MUST 为单向快照；赠票系统 MUST NOT 把签到状态、注册码状态回写给本系统。

### Key Entities

- **接收人（上游）**：姓名、单位、手机号、邮箱、状态（待审批/已通过/已拒绝/已签到/已作废）、所属推荐人与渠道。
- **交接文件**：一份 CSV，代表某一时刻「已通过」接收人的快照。
- **参会人（下游）**：以手机号为唯一键的名单记录，带渠道来源、权益类型、是否参与抽奖。
- **签到记录（下游）**：一人一条，绑定端口号，是现场到场的唯一凭据。

## Success Criteria *(mandatory)*

- **SC-G01**：500 人交接在 10 分钟内完成，全程无需手工改数据库。
- **SC-G02**：导入后的名单人数等于上游「已通过」去重后人数，差异为 0；有冲突时冲突清单可逐条定位。
- **SC-G03**：活动期间本系统签到记录 100% 覆盖到场观众；赠票系统签到记录为 0。
- **SC-G04**：未配置渠道时导入被拒，提示能直接指出渠道名称，运营可自行修正后重导。
- **SC-G05**：同一文件重复导入后名单总数不增加。
- **SC-G06**：管理员账户可在管理端完成新增/停用，启用中始终 ≤3，且最后一个启用管理员无法被停用或删除。
- **SC-G07**：v1 未接入真实发信时，审批链接仍可从邮件出箱在 1 分钟内找到并复制，业务不中断；二期接入企业微信邮后，关键邮件送达率不低于 95%。
- **SC-G08**：现场签到响应时间在正常网络下不超过 3 秒，不因上游系统状态受影响。
- **SC-G09**：上线核对表可在 5 分钟内完成并留档。

## Assumptions

- 赠票系统部署在公网可达地址（独立子域或端口），其 `KCON_SITE_URL` 与实际访问地址一致。
- 赠票系统管理员不超过 3 人，部署时替换为真实运营邮箱。
- 二期接入企业微信邮（腾讯企业邮），使用单一发件邮箱对外发信；v1 暂不启用真实发信，改由邮件出箱复制链接。
- 管理员账户由运维在赠票系统内维护，最多 3 个启用账号；初始管理员通过部署配置注入。
- 本系统已按上游渠道名称配置好渠道映射；映射维护由超管负责。
- 上游接收人手机号可能重复，按 FR-G02 在导出侧去重。
- 本系统现有容量（端口池、名单、签到）满足 500 人规模，无需扩容。
- 活动期间现场只使用本系统签到，赠票系统的注册码仅用于邮件告知与落地页状态查询。

## Out of Scope

- 赠票系统与本系统的实时 API / 双向同步。
- 退票、作废、改签、换渠道的自动同步。
- 统一登录 / SSO / 统一账号体系。
- 在赠票系统内实现签到、抽奖、兑奖、端口号。
- 修改本系统签到、抽奖、兑奖、端口号规则。
- 邮件模板视觉改版与新增邮件类型。
- 本系统数据库结构变更（v1 仅使用既有名单/签到表）。
- 赠票系统统计看板增强（本规格只要求导出与核对能力）。

## 上线前检查清单

### A. 赠票系统（上游）

1. 通过部署配置注入初始管理员邮箱；后续在「管理员账户管理」中新增/停用（启用中 ≤3）。
2. 邮件真实投递暂缓；确认「邮件出箱」可打开、可按模板筛选、可复制链接。二期再接入企业微信邮（单发件邮箱，凭据走环境变量）。
3. 提供「导出已通过接收人 CSV」能力（脚本或管理端入口均可），字段与顺序符合 FR-G01。
4. 不创建签到员账号；不向现场暴露其签到页入口。
5. 配置反向代理与 HTTPS，设置正确的站点地址，确保页面中的链接可打开。
6. 配置 SQLite 数据文件每日备份并保留 7 天。
7. 冒烟：建 1 渠道 → 1 推荐人 → 1 接收人 → 审批 → 从邮件出箱复制链接 → 导出文件中包含该人。

### B. 本系统（下游）

1. 为每个上游渠道配置「渠道来源」映射（权益类型 + 是否参与抽奖）。
2. 以追加模式导入交接 CSV，记录新增/更新数量。
3. 抽 1 人完成签到 → 端口号 → 抽奖 → 兑奖全链路回归。
4. 重复导入同一文件，确认名单总数不变。
5. 确认现场签到入口、抽奖控制台、大屏、兑奖页均可访问。

### C. 联合验收

1. 核对表签字：上游已通过数、导出行数、新增、更新、被拒渠道、重复手机号。
2. 确认活动期间赠票系统签到记录为 0、无签到员账号。
3. 确认本系统签到、抽奖、兑奖不依赖赠票系统在线。
