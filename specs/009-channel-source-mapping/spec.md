# Feature Specification: 渠道来源映射

**Feature Branch**: `feature/014-channel-source-mapping`

**Created**: 2026-10-19

**Status**: 已被 `specs/010-channel-mapping-page` 取代（字典 + 备注方案废弃，改为独立表与独立页面）

**Input**: 渠道来源与权益类型、参与抽奖存在固定对应关系，且映射需要可编辑；导入模板只保留 3 列必填，其余由映射自动带出。

## 背景

新票务导出中，同一渠道来源通常对应固定的权益类型与抽奖资格。让现场人员逐行重复填写既费劲，也容易填出互相矛盾的三列。

> 历史方案（已废弃）：复用 RuoYi 字典管理，用 `remark` 承载「是否参与抽奖」。
> 该方案无法表达强类型，且编辑路径过长，现由 `specs/010-channel-mapping-page` 的独立表方案替代。
> 下文保留原设计仅用于追溯。

## 映射存储

- 字典类型：`kcon_channel_mapping`
- `dict_label`：渠道来源（唯一语义键）
- `dict_value`：权益类型
- `remark`：参与抽奖，填「是」或「否」

编辑入口：系统管理 → 字典管理 → `kcon_channel_mapping`。

初始数据：

| 渠道来源 | 权益类型 | 参与抽奖 |
|---|---|---|
| 重要嘉宾赠票 | 含自助午餐、伴手礼 | 否 |
| 其他（赠票） | 无 | 否 |
| TGO会员（会员权益） | 含自助午餐 | 是 |
| 嘶吼平台卖票 | 含自助午餐、帽衫、伴手礼 | 是 |
| TGO卖票 | 含自助午餐、帽衫、伴手礼 | 是 |
| 海凤卖票 | 含自助午餐、帽衫、伴手礼 | 是 |
| IT资讯平台卖票 | 含自助午餐、帽衫、伴手礼 | 是 |

## Requirements

### Functional Requirements

- **FR-M1**: 导入模板 MUST 只有 3 列必填：姓名、手机号、渠道来源。
- **FR-M2**: 权益类型、参与抽奖、公司、职位、邮箱 MUST 为选填，排在必填列之后。
- **FR-M3**: 导入时 MUST 按渠道来源查询 `kcon_channel_mapping`。
- **FR-M4**: 命中映射时 MUST 以映射的权益类型与参与抽奖为准，忽略行内填写（映射优先）。
- **FR-M5**: 未命中映射时 MAY 使用行内填写的权益类型与参与抽奖；两者都为空时，参与抽奖按「否」入库，权益类型留空。
- **FR-M6**: 未命中映射的行 MUST 在导入结果中计数并列出渠道来源，提示到字典管理补充。
- **FR-M7**: 修改映射 MUST 只影响后续导入，不自动改写已有名单；需要重来时使用现有「数据清场」后重新导入。
- **FR-M8**: 字典数据 MUST 支持增删改停用；停用的条目不参与映射。
- **FR-M9**: 新装库与已有库 MUST 都包含 `kcon_channel_mapping` 初始数据；已有库通过幂等迁移补齐，不覆盖用户已修改的值。
- **FR-M10**: 旧 9 列文件与旧表头 MUST 继续可导入。

### Key Entities

- **Dict Type `kcon_channel_mapping`**: 渠道来源映射。
- **Dict Data**: `dict_label`=渠道来源，`dict_value`=权益类型，`remark`=是/否。

## Success Criteria

- **SC-M1**: 只填姓名、手机号、渠道来源三列即可导入，权益类型与参与抽奖由映射带出。
- **SC-M2**: 字典中修改某个渠道的权益类型/资格后，下一次导入生效，已有名单不变。
- **SC-M3**: 未配置映射的渠道来源不会误进抽奖池，并在导入结果中可见。
- **SC-M4**: 停用的映射条目不参与导入。

## Assumptions

- 渠道来源按去除首尾空格后的精确值匹配 `dict_label`。
- `remark` 只有填「是」表示参与，其他值按「否」。
- 已有名单需要通过「数据清场」后重新导入来应用新映射。

## Out of Scope

- 映射修改后自动刷新历史名单。
- 按渠道来源关键字模糊匹配。
- 映射的审批流或变更历史。
